# 요청 시간 제한

화면이 서버에 보내는 모든 요청(`web/api.ts` 의 `request`)에 제한 시간을 둔다. 이전에는 서버가 응답하지 않으면 요청이 영영 끝나지 않아, 줄 서 있는 작업(이미지 업로드, 장면 추가·삭제)과 새로 불러오기("불러오는 중…")가 멈췄다.

## 값
| 요청 | 제한 시간 | 이유 |
|---|---|---|
| 일반(프로젝트 조회·저장, 장면 추가·삭제, 이미지 삭제, 영상 요청·상태 조회) | 30초 | 모두 빠른 요청이다(영상 만들기는 접수만 하고 바로 돌려준다) |
| 이미지 업로드 | 60초 + MB 당 10초(올림) | 파일이 클수록 오래 걸린다. 10MB 이미지는 160초 — 초당 약 0.5Mbps 까지 견딘다 |

시간은 응답 본문을 다 읽을 때까지 포함한다. 시간 안에 끝나지 않으면 요청을 중단(`AbortController`)하고 `ApiFailure('TIMEOUT')` 로 알린다.

## 화면의 동작
| 상황 | 동작 |
|---|---|
| 저장이 시간 초과 | "저장하지 못했어요 [다시 저장]". 다시 저장하면 최신 본문을 다시 보낸다(저장은 멱등이라 서버가 이미 처리했어도 안전) |
| 장면 추가·삭제가 시간 초과 | **서버가 처리했는지 알 수 없다.** 같은 요청을 다시 보내면 장면이 중복되거나 엉뚱한 장면이 지워지므로, 재시도 대신 안내 띠("서버 응답이 없어서 장면을 바꿨는지 알 수 없어요. 새로 불러와 확인해 주세요")와 [새로 불러오기]를 보인다. **이 상태(그리고 다른 곳에서 장면이 바뀐 상태)에서는 "+ 장면 추가"와 "장면 삭제" 버튼이 비활성화되고, 훅(`changeScenes`)도 요청을 보내지 않는다.** 새로 불러와 서버의 실제 구성을 읽으면 풀린다 |
| 이미지 업로드·삭제가 시간 초과 | 토스트로 알린다. 줄 서 있던 다음 작업은 이어서 실행된다 |
| 새로 불러오기 | 나간 요청이 끝나기를 기다리되, 각 요청에 제한 시간이 있으므로 기다림이 무한하지 않다(최대 업로드 제한 시간). 불러오기 자체가 시간 초과면 "프로젝트를 불러오지 못했어요 [다시 불러오기]" |
| 영상 요청이 시간 초과 | 토스트로 알린다. 서버가 이미 접수했다면 다시 누를 때 진행 중이라는 응답(`RENDER_IN_PROGRESS`)으로 진행 화면으로 이동한다 |

## 진단·테스트용 조정
`window.__SM_TIMEOUT_MS` 가 숫자면 모든 요청의 제한 시간이 그 값이 된다. E2E 가 응답이 없는 서버를 빨리 흉내 내려고 1.5초로 줄여 쓴다. 평소에는 설정하지 않는다.

## 검증
- 단위 `tests/requestTimeout.test.ts`(3개): 일반 30초, 업로드 계산(올림), 10MB 160초
- E2E 3개(`e2e/editor.e2e.ts`): 응답 없는 저장 → 저장 실패 표시 후 다시 저장, 서버는 처리했지만 응답이 없는 장면 추가 → 결과를 알 수 없다는 안내와 새로 불러오기(서버에는 4개, 재시도했다면 5개였을 것), 영영 응답하지 않는 업로드가 줄에 있어도 새로 불러오기가 끝남
- 변이 검사: 요청에 중단 신호를 붙이지 않으면 위 3개 중 저장·추가·새로 불러오기 테스트가 실패하고, 추가 시간 초과를 "알 수 없음"으로 표시하지 않으면 추가 테스트가 실패한다(확인 후 원복). 처음에는 저장 테스트가 변이를 통과시켰다 — 테스트의 서버 흉내가 6초 뒤 연결을 끊어 시간 제한이 없어도 "저장 실패"가 되었기 때문이다. 응답을 영영 하지 않도록 고쳐 이 테스트도 시간 제한을 직접 검증한다.

## 검수 반영 (PR #4, P2)
- **지적**: 장면 추가가 시간 초과되어 `'unknown'` 이 되어도 "+ 장면 추가" 버튼이 다시 켜지고 `changeScenes` 가 충돌 상태를 보지 않아, 입력이 없으면 같은 POST 가 한 번 더 나가 장면이 5개가 된다(처음 문서·PR 본문은 "재시도 대신 새로 불러오게 한다"고 했지만 실제로는 막지 못했다).
- **처리**: 충돌 상태(`'changed'`·`'unknown'`)에서는 장면 추가·삭제 버튼을 비활성화하고, `changeScenes` 도 충돌 상태(`conflictRef`)를 확인해 요청을 보내지 않고 안내한다. 상태는 비동기 흐름에서 낡은 값을 읽지 않도록 ref 에도 둔다.
- **검증**: 두 방어를 따로 확인한다. 버튼은 E2E 가 비활성화 여부를 보고(속성을 떼도 React 가 prop 으로 클릭을 무시하므로 DOM 클릭으로는 훅을 시험할 수 없다), 훅은 **미리 열어 둔 삭제 확인 창**(확인 버튼에는 비활성화 조건이 없어 훅까지 도달)으로 시험한다. 서버로 삭제 요청이 나가지 않고 장면 수가 그대로여야 통과한다. 변이 검사: 버튼 비활성화를 빼면 첫째 테스트가, 훅의 검사를 빼면 둘째 테스트가 실패한다(확인 후 원복).
- **작업 중 기록**: 처음에는 훅의 방어를 "속성을 뗀 버튼 클릭"으로 시험하려 했지만, React 가 prop 기준으로 클릭을 무시해 요청이 아예 나가지 않았다. 훅 방어를 제거한 변이가 통과해서 테스트가 아무것도 검증하지 못한다는 것을 알았고, 디버그 출력으로 원인을 확인한 뒤 위 방식으로 다시 짰다.

### 검수 반영 2 (PR #4, P2): 영상 만들기도 막는다
- **지적**: 장면 삭제가 서버에서는 성공했지만 응답이 시간 초과되면 `'unknown'` 인데도 영상 만들기가 가능했다. `saveNow()` 는 저장할 변경이 없으면 통과하고 `startRender` 는 `structuring` 만 봤다. 확인 창은 이전 장면 수·길이를 보여 주는데 서버는 줄어든 장면 목록으로 스냅샷을 만들어 다른 영상이 만들어진다.
- **처리**: 충돌 상태(`'changed'`·`'unknown'`)에서는 헤더의 "영상 만들기" 버튼을 비활성화하고, `startRender` 도 요청을 보내지 않고 확인 창을 닫으며 "장면 구성을 먼저 새로 불러와 주세요"를 안내한다. 새로 불러오면 풀린다.
- **검증**: 미리 열어 둔 영상 만들기 확인 창(시작 버튼에는 비활성화 조건이 없어 `startRender` 까지 도달)에서 결과 불명 상태를 만든 뒤 시작을 누른다. 영상 요청이 나가지 않고(`renders/latest` 가 null), 확인 창이 닫히고, 헤더 버튼이 비활성화되어야 통과한다. 변이 검사: `startRender` 의 검사를 빼면 영상 요청이 나가 실패하고, 헤더 버튼 비활성화를 빼면 버튼 검사에서 실패한다(확인 후 원복).
- **작업 중 기록**: 주석 일부만 치환해 뒷부분이 코드 줄에 남는 구문 오류를 만들었다. 타입체크 오류가 났는데도 테스트를 돌려 **빌드가 실패한 채 이전 번들로 실행**되었고, 그 결과(정상 실패, 변이 3개 모두 같은 실패)가 모두 무효였다. 오류를 고친 뒤 빌드 성공과 `dist` 갱신 시각을 확인하고 정상 경로와 변이를 다시 검증했다. 이후 변이 검사는 빌드 성공을 확인한 뒤에만 테스트를 돌린다.

## 한계
- 제한 시간 값(30초, 업로드 160초)은 로컬 서버 기준의 보수적인 값이다. 느린 네트워크·원격 배포에서는 조정이 필요할 수 있다.
- 시간 초과한 요청이 서버에서는 처리된다. 저장은 멱등이라 문제없고, 장면 추가·삭제는 위처럼 새로 불러오게 한다. 이미지 업로드가 시간 초과 후 서버에서 완료되면 장면에 이미지가 붙어 있지만 화면은 모를 수 있다(새로 불러오면 보인다).
- 서버 쪽 요청 처리 시간 제한(느린 렌더 등)은 이 문서의 범위가 아니다. 렌더는 별도로 `RENDER_TIMEOUT_MS` 를 쓴다.
