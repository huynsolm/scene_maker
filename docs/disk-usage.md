# 디스크 사용량 측정

`npm run measure:disk` (`scripts/measure-disk.ts`)로 쟀다. 실제 앱의 저장·렌더·정리 경로를 그대로 쓰며, 프로젝트 한 개의 생애(업로드 → 영상 만들기 → 이미지를 바꿔 다시 만들기 → 지난 영상 삭제 → 프로젝트 삭제)를 따라가며 데이터 폴더의 각 부분을 `du`(블록 단위)로 잰다. `--only P1,P2`로 케이스를 고를 수 있다.

**환경**: 4 코어, 16GB, 클라우드 샌드박스. 이미지는 합성(testsrc2 + 잡음)이라 압축률이 실제 사진과 다를 수 있다.

## 읽는 법과 결론

| 항목 | 측정값 | 의미 |
|---|---|---|
| 업로드한 이미지 | 휴대폰 사진 1장 4.9MB, 10장 **49MB**. 4096x4096 사진은 1장 6.6MB, 10장 66MB | **원본을 그대로** 저장한다. 앱이 허용하는 최대는 이미지 1장 10MB x 장면 10개 = 프로젝트당 약 100MB |
| 임시 폴더 | 렌더 중 최대 **24~30MB**, 끝나면 **0**(파일 0개) | 이미지 사전 줄이기가 만드는 프레임 PNG와 결과 파일이다. 작업이 끝나면 지워진다. 동시에 렌더는 한 번에 하나라 겹치지 않는다 |
| 완성 영상 | 100초 영상 2.7MB, 300초 영상 8.1MB | **자동으로 지우지 않는다**(사용자 결정). 영상을 만들 때마다 한 편씩 쌓이고, 결과 화면에서 하나씩 지울 수 있다 |
| DB | 112KB에서 시작해 영상 한 편당 약 50~60KB 증가 | 무시할 수 있다. 프로젝트를 지워도 파일 크기는 줄지 않지만 비워진 공간을 다시 쓴다 |
| 프로젝트 삭제 | 이미지·영상·임시 **모두 0개로 회수** | 삭제는 이미지와 영상 파일까지 지운다(확인 창으로 먼저 알린다) |

### 가장 중요한 점: 이미지를 바꿔 다시 만들수록 계속 쌓인다
- 이미지 3장을 바꿔 영상을 다시 만들 때마다 **약 17MB**가 늘었다(이전 이미지 3장 14.7MB + 새 영상 2.7MB). 3회 반복 뒤 이미지 92MB, 영상 11MB(파일 19개 + 4개).
- 이전 이미지가 남는 이유: 영상 만들기 요청은 그 시점의 이미지를 참조하고, 이전 영상 작업이 그 이미지를 참조하는 동안은 지우지 않는다(사용자 결정: "완성 영상은 자동 삭제하지 않는다, 이전 이미지는 어떤 작업도 참조하지 않을 때만 지운다"). 영상이 자동으로 지워지지 않으므로 그 영상이 참조하는 이미지도 계속 남는다.
- **바뀌는 장면 수 x 반복 횟수만큼 선형으로 늘고 상한이 없다.** 휴대폰 사진 기준 "3장 바꾸고 다시 만들기"를 50번 하면 약 850MB다. 장면마다 10MB 사진을 매번 바꾸면 훨씬 빠르다.
- 프로젝트를 삭제하면 모두 회수된다. 즉 쌓이는 곳은 "오래 고쳐 가며 쓰는 프로젝트"다.

### 지난 영상을 지우면 얼마나 회수되나 (실측)
결과 화면의 개별 삭제(`DELETE /api/projects/:id/renders/:jobId`)로 쌓인 영상을 지운 뒤, 디스크에 남은 파일이 **필요한 파일과 정확히 같은지** 스크립트가 매번 검사한다(다르면 스크립트가 실패한다). 필요한 파일 = 현재 장면이 쓰는 이미지 ∪ 남은 작업이 참조하는 이미지, 그리고 남은 작업의 영상이다.
- P1(영상 4편, 이미지 19장 92MB + 영상 11MB): 오래된 3편을 지우자 **이미지 19→10장(92→49MB), 영상 4→1편(11→2.7MB)**. 최신 영상 1편과 현재 장면의 이미지 10장만 남았다. 마지막 영상까지 지우면 영상 0편, 이미지는 현재 장면이 쓰는 10장(49MB)만 남는다. 모든 단계에서 남은 파일이 필요한 파일과 일치했다.
- P2(영상 1편): 지울 오래된 영상이 없어 변화가 없고, 마지막 영상을 지우면 영상 8.1MB만 회수된다(장면이 쓰는 이미지 66MB는 그대로).
- 즉 **"쌓이는" 증가분은 이전 영상을 지우면 함께 사라진다.** 다만 서버 응답의 `removedImages` 같은 개수는 물리적 공간 회수량이 아니다 — 위 표의 `du` 값으로 읽어야 한다.
- 이 숫자도 이 환경 한 곳에서 쟀다. Windows 등에서 재생·다운로드 중인 영상은 잠금으로 파일 삭제가 실패할 수 있고, 그때는 기록만 지워지고 파일은 다음 서버 시작 때 정리된다(이 측정에는 넣지 않았다).

## 한계
- 한 대의 4코어 환경에서 케이스당 한 번 쟀다. 합성 이미지를 썼다.
- 서버가 렌더 도중 갑자기 멈췄을 때 남는 임시 폴더와 고아 파일의 회수(서버 시작 시 정리)는 이 측정에 넣지 않았다. 별도로 확인해야 한다.
- 이전 영상은 사용자가 결과 화면에서 하나씩 지울 수 있다(자동 삭제·일괄 삭제는 없다). 실패한 작업 기록이 붙잡는 이미지는 회수 대상이 아니다.
- DB 크기(KB)는 실행마다 조금 다르다(표의 일부 행은 이전 실행의 값).
