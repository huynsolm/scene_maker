# 계획: 실패한 작업이 붙잡은 이미지 회수

상태: **1단계(서버·테스트) 구현 완료 — `99d2342`**, 2단계(실측·문서) 남음. 기준 코드: `main` 337a2a5.

## 1. 목적
영상 만들기가 실패하면 그 작업 기록은 남고, 작업이 참조하던 업로드 이미지도 함께 남는다. 실패한 작업은 다시 렌더되지 않으므로 이 이미지는 쓰이지 않는데, 회수 조건("어떤 장면·작업도 참조하지 않음")을 영영 만족하지 못해 디스크에 쌓인다. 이미지를 바꿔 가며 실패를 반복하면 원본 사진(장당 수 MB)이 계속 늘어난다. 이 이미지를 안전하게 회수한다.

## 2. 현재 구조 (코드 확인 결과)
- 작업을 만들 때 스냅샷의 장면마다 `render_job_images(job_id, image_id)` 연결을 넣는다(`server/renderStore.ts` `createJob`).
- 이미지는 **렌더하는 동안에만** 필요하다. `sceneInputs()`가 스냅샷의 `imageId`로 파일 경로를 얻어 렌더러에 넘긴다. 단, 이것은 **작업 쪽**의 이야기다. 현재 장면이 쓰는 이미지는 `scenes.image_id`로 따로 보호되며, 회수는 이 보호를 그대로 지켜야 한다(`collectImageIfUnused`가 장면 참조를 확인한다).
- 작업이 끝나면 `finish(jobId, 'done' | 'failed')`가 상태를 바꾼다. 연결은 어느 경우에도 남는다.
- 실패한 작업은 다시 렌더되지 않는다. 결과 화면의 "다시 시도"는 `createRender(projectId)`로 **현재 프로젝트 내용으로 새 작업**을 만든다. 상태 흐름 `waiting → generating → done/failed`는 **코드 경로로만 지켜지고 DB 제약(CHECK·트리거)으로 강제되지는 않는다**. 실패 작업을 다시 활성으로 돌리는 코드가 생기면 이 계획의 전제가 깨진다.
- 결과 화면은 실패 작업의 이미지를 표시하지 않는다(장면 문구·길이만). API 응답(`toView`)에는 장면별 `imageUrl`이 들어 있지만 화면에서 쓰는 곳이 없다.
- 업로드 검사(`server/store.ts:316` `inspectImage`)는 **헤더만 본다**(전체 디코딩을 하지 않는다). 그래서 헤더만 맞는 손상 이미지도 업로드되고, 렌더 단계에서야 실패한다(`tests/ffmpeg.test.ts:322`가 120바이트로 자른 PNG로 이 경로를 이미 확인한다).
- 이미지 회수: `Store.collectImageIfUnused(imageId)`는 장면과 `render_job_images` 어디에서도 참조하지 않으면 행과 파일을 지운다. 서버 시작 시 `sweepOrphans()`도 참조 없는 이미지 행과 파일을 지운다.
- 서버 시작 순서(`server/app.ts`): `failInterrupted()` → `sweepFiles()` → `sweepOrphans()`.
- 렌더 큐(`server/renderQueue.ts` `runJob`)는 렌더 실패를 `catch` 안에서 `renders.fail()`로 처리한다. 따라서 `fail()`이 예외를 던지면 큐 밖으로 새어 나간다.

## 3. 결정 (사용자 확인)
| 항목 | 결정 |
|---|---|
| 회수 방식 | **실패하는 순간 자동으로 회수**: 작업이 실패하면 이미지 연결을 끊고, 아무도 쓰지 않는 이미지는 지운다. 실패 기록과 오류 안내는 그대로 남긴다. 화면 변경 없음 |
| 기존 실패 기록 | **다음 서버 시작 때 회수**: 이미 쌓인 실패 작업의 연결을 정리하고, 기존 시작 시 정리(`sweepOrphans`)가 쓰지 않는 이미지를 지운다 |
| 유지되는 결정 | "실패 기록 삭제는 범위 밖"은 그대로다. 실패 기록 행은 지우지 않고 이미지 연결만 끊는다. 실패 기록 삭제 요청은 계속 409 |

## 4. 설계

### 4.1 실패할 때 (`RenderStore.fail` → `finish`)
1. `finish(jobId, 'failed', …)`가 지금처럼 상태를 `failed`로 바꾸고 프로젝트 상태를 갱신하는 트랜잭션을 **먼저 커밋**한다. 이 부분은 바꾸지 않으며, **이 트랜잭션의 예외는 지금처럼 그대로 던진다**(삼키지 않는다).
2. 커밋 뒤(실패일 때만) 세 단계를 거친다. 그 작업의 연결 이미지 id를 읽고, `DELETE FROM render_job_images WHERE job_id = ?`를 실행한 다음, 읽어 둔 이미지마다 `collectImageIfUnused(id)`를 호출한다. 완료(`done`)일 때는 하지 않는다(완성 영상은 이미지를 계속 참조한다 — 영상 삭제 때 회수).
3. 2의 전체를 **최선만 다한다**. 이미지 id 읽기·연결 삭제·이미지 회수 중 어디서 예외가 나든 로그만 남기고 계속한다. 이미지 회수는 이미지마다 따로 감싸, 한 장이 실패해도 나머지는 처리한다. 실패 기록은 이미 커밋됐으므로 뒤집히지 않는다. 연결이 남더라도 해가 없고(이미지가 남을 뿐) 다음 서버 시작의 4.2가 정리한다.
4. 다른 장면·완성 작업·진행 중 작업이 같은 이미지를 참조하면 `collectImageIfUnused`가 남긴다(기존 규칙 그대로).
- 자체 검토 반영: 처음에는 연결 삭제를 상태 변경과 **같은 트랜잭션**에 두었다. 그러면 연결 삭제가 실패할 때 실패 기록까지 롤백되어 작업이 '생성 중'으로 갇힌다. 상태 기록이 회수보다 중요하므로 순서를 나눴다.
- 범위: 이 변경은 **회수 후처리가 큐 밖으로 예외를 내지 않게** 할 뿐이다. `runJob`의 다른 실패 경로(상태 트랜잭션 자체의 예외, `finally`의 `fs.rmSync(workDir)` 예외)는 바꾸지 않으며, 큐의 내구성 전체를 해결한다고 주장하지 않는다.

### 4.2 서버 시작 시 (기존 실패 기록)
- `RenderStore.releaseFailedImages()`를 새로 둔다: `DELETE FROM render_job_images WHERE job_id IN (SELECT id FROM render_jobs WHERE status = 'failed')`. 몇 개를 정리했는지 돌려준다.
- 시작 순서: `failInterrupted()`(중단된 작업도 4.1로 정리됨) → **`releaseFailedImages()`** → `sweepFiles()` → `sweepOrphans()`(참조가 사라진 이미지 행·파일 회수).
- 매 시작마다 실행해도 안전하다(멱등). 이미 정리됐으면 지울 것이 없다.
- **실패 정책**: `releaseFailedImages()`의 예외는 로그만 남기고 시작을 계속한다. 연결이 남으면 이미지가 남을 뿐이고 다음 시작 때 다시 시도된다. 이 처리는 이 호출에만 적용한다. `failInterrupted()` 등 필수 DB 작업의 예외는 지금처럼 시작을 실패시킨다.

### 4.3 API 응답
- 실패 작업의 `toView`가 돌려주는 장면별 `imageUrl`은 이미지가 지워진 뒤 404가 된다. 화면은 쓰지 않지만 계약을 분명히 하려고, **실패 작업은 `imageUrl: null`**로 돌려준다(`shared/types.ts`의 타입을 `string | null`로).
- 기준은 **상태가 `failed`인지 하나**다. 회수가 성공했는지, 이미지가 아직 남아 있는지와 무관하게 실패 작업이면 항상 `null`이다(응답이 디스크 상태에 따라 흔들리지 않게).
- 이미지 파일 이름(`imageFileName`)은 스냅샷에 있으므로 그대로 둔다.

### 4.4 동시성·실패 정책
- 서버는 단일 프로세스이고 better-sqlite3·파일 작업은 동기 실행이다. 그래서 4.1의 트랜잭션과 회수 사이에 다른 요청(같은 이미지를 장면에 다시 붙이는 요청, "다시 시도"의 새 작업 생성 등)이 끼어들지 않는다(기존 삭제 기능과 같은 전제). 새 작업이 먼저 연결을 넣었다면 `collectImageIfUnused`가 그 연결을 보고 남긴다.
- 파일 삭제 실패(잠금·권한)는 `safeRm`이 흡수하고, 남은 행·파일은 다음 시작의 `sweepOrphans`가 정리한다.

### 4.5 바뀌지 않는 것
- 실패 기록, 오류 제목·설명·장면 번호, "다시 시도", 실패 화면.
- 완성 영상이 참조하는 이미지(영상을 지울 때 회수).
- 진행 중 작업과 현재 장면이 참조하는 이미지.

## 5. 검증 계획

### 5.1 API·단위 테스트 (`FakeRenderer.failWith`)
기본 동작:
- 실패하면 그 작업의 연결이 사라지고, 그 작업만 쓰던 이미지(장면에서 이미 교체된 이미지)의 행·파일이 지워진다.
- 같은 이미지를 **현재 장면 / 완성 작업 / 진행 중 작업**이 쓰면 남는다(각각).
- **완성 작업 보호**: 완성 작업과 실패 작업이 같은 이미지를 공유할 때, 실패 뒤에도 이미지와 완성 작업의 연결이 남는다(변이 "완료 작업에도 연결 삭제"를 잡는 테스트).
- **여러 실패 작업이 공유한 옛 이미지**: 같은 이미지를 참조한 실패 작업이 여럿이면, 모두 실패한 뒤(그리고 장면이 그 이미지를 더는 쓰지 않으면) 이미지가 회수된다. 하나만 실패한 시점에는 아직 실패하지 않은 쪽의 참조 때문에 남는다.
- 실패 기록·오류 정보는 그대로 남고, 실패 기록 삭제는 여전히 409.
- 실패 작업의 응답 `imageUrl`은 `null`, 완성 작업은 그대로. 회수가 실패해 이미지가 남아 있어도 `null`이다.
- 실패 뒤 "다시 시도"(새 작업)는 현재 장면 이미지로 정상 렌더된다.

실패 주입(4.1의 세 단계를 각각 따로 깨뜨린다). 각 경우 상태는 `failed`로 남고, 큐가 멈추지 않아 다음 작업이 처리되며, 남은 연결·이미지는 다음 시작 때 정리됨을 확인한다:
- **이미지 id 읽기 실패**.
- **연결 삭제 실패**.
- **첫 이미지 회수 실패**: 두 번째 이후 이미지는 정상 회수된다.

서버 시작:
- 연결이 남은 실패 기록(기존 데이터 흉내)을 DB에 직접 만든 뒤 재시작하면, 연결이 정리되고 이미지 행·파일이 회수된다. 한 번 더 재시작해도 문제없다(멱등).
- **충돌 복구 두 경우**: (a) 상태 커밋 뒤 연결 삭제 전에 멈춘 상태(실패 작업 + 연결 남음), (b) 연결 삭제 뒤 이미지 회수 전에 멈춘 상태(실패 작업 + 연결 없음 + 이미지 행·파일 남음). 각 상태를 DB·파일로 만든 뒤 재시작하면 회수된다.
- 중단된 작업(`failInterrupted`)도 시작 시 연결이 정리된다.
- `releaseFailedImages()`가 던져도 서버는 시작되고, 다음 시작에서 정리된다.

### 5.2 변이 검사
다음 각각에 대해 대응 테스트가 실패하는지 확인한다.
- 연결 삭제 제거
- 회수 호출 제거
- 이미지별 예외 처리 제거
- 후처리 전체 예외 처리 제거
- 시작 시 `releaseFailedImages` 호출 제거
- 시작 시 실패 정책 제거(예외 전파)
- 완료 작업에도 연결 삭제(완성 영상 이미지가 지워지는지)
- `imageUrl` 기준을 상태 대신 "이미지 존재"로 바꾸기

### 5.3 실측 (`npm run measure:disk`)
- 새 단계: 실패하는 렌더를 이미지를 바꿔 가며 몇 번 반복한다. 렌더를 실패시키려고 **헤더만 맞는 손상 이미지를 직접 업로드**한다(업로드 검사는 헤더만 본다 — §2). 업로드 뒤 저장된 파일을 자르는 방식은 쓰지 않는다. 회수 전에 디스크 사용량이 줄어 측정이 왜곡되기 때문이다.
- 판정은 두 가지를 따로 본다.
  1. 측정 전에 **남아야 할 이미지 id 집합**(현재 장면 이미지 ∪ 비실패 작업의 이미지)을 따로 계산해 저장해 두고, 디스크의 실제 이미지 파일과 정확히 같은지 비교한다(기존 `verify()`의 계산에만 기대지 않는다).
  2. 현재 장면이 쓰는 이미지가 모두 남아 있는지 **독립적으로** 확인한다.
- 바꾸기 전에는 실패할 때마다 이미지가 쌓이고, 바꾼 뒤에는 쌓이지 않음을 숫자로 기록한다.

### 5.4 E2E
화면 변경이 없으므로 새 E2E는 두지 않는다. 기존 실패 화면 E2E가 그대로 통과해야 한다.

## 6. 위험과 한계
- 실패 원인이 된 이미지를 사용자가 이미 다른 사진으로 바꿨다면 옛 이미지는 지워진다(이후에 쓸 곳이 없다). 아직 바꾸지 않았다면 현재 장면이 쓰므로 남는다.
- 앞으로 "실패한 작업과 같은 스냅샷으로 다시 시도" 같은 기능을 만들거나 실패 작업을 다시 활성으로 돌리는 경로를 만들면 이 결정을 다시 봐야 한다(그때는 이미지가 필요하다). 상태 흐름은 DB로 강제되지 않는다(§2).
- 실패 작업의 API `imageUrl`이 `null`로 바뀐다(API 계약 변경, 현재 소비자는 없음).
- 시작 시 정리는 실패 작업 기록을 훑으므로 **비용이 작업 기록 수에 비례한다**. 단일 사용자 앱의 기록 규모에서는 작다고 보지만, 공짜는 아니다.
- 큐 내구성은 회수 후처리에 대해서만 다룬다(§4.1 범위). `runJob`의 `finally` 정리 예외 등은 그대로다.
- 단일 프로세스·동기 실행 전제는 기존과 같다.
