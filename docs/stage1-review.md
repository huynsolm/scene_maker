# 1단계 구현 보고 · Codex 검수용

범위: 프로젝트·장면 저장, 이미지 업로드, 프로젝트 목록, 편집 화면. 렌더링(2단계)·결과 화면(3단계)은 포함하지 않는다.
디자인 기준: `design_handoff_scene_maker/README.md` 와 `Scene Maker.dc.html` (이 저장소에는 포함하지 않음).

## 1. 결정 사항과 디자인 문서의 차이

사용자가 확정한 값이 디자인 README 의 값과 다른 곳은 **사용자 결정을 우선**했다.

| 항목 | 디자인 README | 적용한 값 |
|---|---|---|
| 출력 해상도 | 1920 × 1080 | **1280 × 720, 30fps**, 무음 MP4 |
| 장면 길이 | 3–20초 | **정수 3–30초** |
| 이미지 형식 | JPG · PNG, 10MB | **JPEG · PNG · WebP**, 10MB, 한 변 4096px 이하 |
| 샘플 이미지 버튼 | 데모용 [예시 이미지 넣기] (제품 포함 여부 미정) | **넣지 않음**. 샘플은 샘플 프로젝트로 대체 |

디자인에 없어서 **추가한** 것 (같은 스타일 토큰 사용, 확인 필요):
- 프로젝트 삭제: 목록 행의 [삭제] + 확인 모달. 문구는 "삭제하면 올려 둔 이미지와 만든 영상 파일도 함께 지워지고, 되돌릴 수 없어요."
- "샘플" 태그(목록·편집 상단·장면 썸네일·이미지 행)와 미리보기 위 "샘플 이미지 · 실제 이미지가 아니에요".
- 장면 길이 직접 입력이 범위를 벗어났을 때 안내("3초에서 30초 사이 정수로 맞췄어요").
- 프로젝트 없음 / 불러오기 실패 / 목록 불러오기 실패 화면, 이미지 업로드 중 표시.
- 목록 마지막 열을 110px → 150px 로 넓혔다([삭제] 버튼 때문).

## 3. 중요한 설계 결정 (검수 포인트)

### A. 데이터 구조 (2단계를 고려한 부분)
- `projects.status` 는 `editing|waiting|generating|done|failed`. 완료/실패 프로젝트를 고치면 서버가 `editing` 으로 되돌린다(`Store.touch`). 대기/생성 중에는 상태를 건드리지 않는다.
- **중복 생성 방지는 DB 제약**으로 건다: `render_jobs` 의 부분 유니크 인덱스 `ON render_jobs(project_id) WHERE status IN ('waiting','generating')`. 2단계에서 요청 API 는 이 제약 위반을 "기존 작업 반환"으로 처리하면 된다. (테스트: `상태 전환 · 중복 방지용 제약`)
- `render_jobs.snapshot_json` 에 요청 시점의 제목·장면 내용을 복사해 두는 용도다. 생성 중 편집은 `scenes` 만 바꾸므로 진행 중 작업과 섞이지 않는다.
- `render_job_images` 로 "어떤 작업이 어떤 이미지를 쓰는지"를 기록한다. 이전 이미지 정리가 이 표를 본다.

### B. 자동 저장과 입력 보존 (`web/useProjectEditor.ts`)
- 제목·문구·길이(`draft`)는 화면이 소유하고, **저장 응답으로 덮어쓰지 않는다**. 그래서 저장 중·실패 중에도 입력이 사라지지 않는다.
- 저장은 동시에 1건만 보낸다. 보내는 동안 더 고쳐졌으면(버전 번호 비교) 끝난 뒤 최신 draft 를 이어서 보낸다.
- 실패하면 `저장하지 못했어요 + [다시 저장]`. 다시 저장이나 다음 입력이 최신 draft 를 재전송한다.
- 저장 안 된 변경이 있으면 새로고침/탭 닫기 시 브라우저 확인(`beforeunload`), 실패 상태에서 [← 프로젝트] 는 `window.confirm`, 정상 이탈 시에는 마지막 변경을 한 번 더 전송한다.
- 이미지는 자동 저장과 분리해 즉시 업로드한다. 서버 응답에서는 이미지 정보만 반영한다.

### C. 이미지 검증과 저장 (`server/imageInspect.ts`, `Store.attachImage`)
- 확장자와 `Content-Type` 은 **신뢰하지 않는다**. `image-size` 로 파일 머리 시그니처를 읽어 JPEG/PNG/WebP 만 허용하고 해상도(≤4096)를 확인한다. 저장 확장자는 판별된 실제 형식을 따른다.
- 10MB 는 두 겹으로 막는다: multipart `fileSize` 한도, 그리고 버퍼 길이 재확인.
- 저장 경로: `data/uploads/<projectId>/<imageId>.<ext>`. 두 ID 모두 서버가 만든 UUID 이고 경로 조립 시 형식을 다시 확인한다(`safeSegment`). 원본 파일명은 표시용으로만 DB 에 저장하며 경로 구분자·제어문자를 제거한다.
- 쓰기 순서: 임시 파일(`.part`) → 이름 변경 → DB 트랜잭션. DB 단계가 실패하면 파일을 지우고, **기존 이미지는 그대로** 남는다.
- 이미지 응답은 `X-Content-Type-Options: nosniff`, 저장된 MIME 으로만 내보낸다.

### D. 파일 정리 정책 (구현 계획 기록, 결정 7)
| 시점 | 동작 |
|---|---|
| 장면 이미지 교체/삭제 | 이전 이미지를 **즉시** `collectImageIfUnused` 로 확인. 장면에서도, 렌더 작업(`render_job_images`)에서도 참조하지 않을 때만 DB 행+파일 삭제 |
| 프로젝트 삭제 | UI 가 안내 모달로 확인 → `DELETE`. 서버는 **생성 중이면 409 로 거부**. 그 외에는 DB 행(연쇄 삭제) → 업로드·영상 폴더 순으로 삭제 |
| 서버 시작 | `sweepOrphans`: `.part` 임시 파일, 어디에도 쓰이지 않는 이미지, DB 에 없는 파일 삭제. 제목·문구·길이와 장면이 쓰는 이미지는 건드리지 않음 |
| 완성 영상 | 첫 버전에서는 **자동 삭제하지 않음**. 프로젝트 삭제 때만 지움 |
| (2단계 예정) 서버 시작 시 `waiting/generating` 작업 | `failed(서버 재시작)` 로 표시하고 사용자가 재시도. 불완전한 임시 영상 파일 삭제 |

DB 를 먼저 지우고 파일을 나중에 지우므로, 중간에 실패해도 남는 것은 고아 파일이며 다음 시작 때 정리된다.

### E. 화면–영상 일치를 위한 준비
자막 위치·크기 비율(좌우 10%, 아래 11%, 글자 크기 = 너비의 3.2%, 줄 간격 1.45)을 `shared/limits.ts` 의 `SUBTITLE` 에 두고 미리보기가 그 값을 읽는다. 2단계 렌더러도 같은 값을 읽을 예정이다. **미리보기와 실제 영상이 같다고 가정하지 않으며**, 2단계에서 출력 프레임과 비교해 차이를 보고한다.

요청하신 검증 항목별 근거:
- **저장 후 새로고침**: E2E `빈 목록에서 첫 영상 만들기…`, API `저장한 제목·문구·길이는…서버를 다시 띄워도 남는다`
- **누락된 이미지·문구**: E2E `영상 만들기 확인`(7개 누락·[채우기] 이동·시작 버튼 비활성), 단위 `findMissing`
- **잘못된 길이**: API 가 2·31·0·음수·소수·문자열·null 거부(거부 시 기존 값 불변), 경계 3·30 허용; E2E 가 범위 밖 입력 보정·안내·−/+ 경계
- **잘못된 이미지**: API+E2E 가 가짜 PNG(텍스트), GIF, 4097px, 10MB 초과, 빈 파일, 잘못된 장면 번호 거부 및 기존 이미지 유지. 경로 문자 파일명 무해화
- **저장 실패 시 입력 보존**: E2E 가 네트워크 실패와 서버 400 모두에서 입력 유지 → [다시 저장] → 새로고침 후 값 확인. 저장 중 추가 입력 시 마지막 값 저장
- **긴 한국어 문구·좁은 화면**: E2E 가 76자 문구의 자막이 프레임·좌우 10% 안에 머무는지, 390/320px 에서 가로 스크롤이 없는지 확인
- **재시작**: API 가 서버를 닫고 같은 데이터 폴더로 다시 열어 내용 유지, 임시/고아 파일 정리, 사용 중 이미지·입력 보존 확인
- **삭제**: E2E 가 안내 문구 표시 → 취소 시 유지 → 확정 시 파일까지 삭제. API 가 생성 중 삭제 거부(409) 확인

테스트가 잡은 실제 버그 1건: 길이 입력에 공백만 넣으면 `Number('')===0` 때문에 오류 없이 3초로 바뀌던 문제 → 빈 값으로 처리하도록 수정(`web/rules.ts`).

## 5. 확인하지 못한 것 / 한계

- **디자인과의 픽셀 대조는 하지 않았다.** 토큰과 문구는 README 에서 옮겼고 스크린샷을 눈으로 비교했을 뿐이다. Pretendard·JetBrains Mono 는 CDN 에서 불러오므로 오프라인에서는 대체 글꼴로 보인다(이 환경에서 CDN 로드 여부는 확인하지 못함).
- **JPEG/WebP 는 실제 카메라 파일이 아니라 헤더만 흉내 낸 합성 데이터로 테스트**했다. 헤더만 정상이고 본문이 손상된 이미지는 업로드 단계에서 걸러지지 않는다. 2단계에서 ffmpeg 디코딩 실패를 `failed` 로 표시하는 처리가 필요하다.
- 드래그 앤 드롭 업로드, 미리보기 재생 버튼, [← 프로젝트]의 `window.confirm`, 브라우저 `beforeunload` 는 자동 테스트하지 않았다.
- 같은 프로젝트를 두 탭에서 동시에 편집하면 **마지막 저장이 이긴다**(충돌 감지 없음). 단일 사용자 가정.
- `npm run dev` 는 서버·Vite 기동과 `/api` 프록시, 새로고침 시 화면 경로 복구를 `curl` 로만 확인했다.
- Chromium 외 브라우저, 실제 모바일 기기, Windows/macOS 는 확인하지 않았다.
- 서버 재시작 시 진행 중 작업을 실패로 바꾸는 처리, 렌더 API, 결과 화면, Noto Sans KR 글꼴 파일과 라이선스 전문 관리는 **2단계 범위로 아직 없다**. 편집 화면의 "영상 만들기 시작" 버튼은 항상 비활성이고 "임시 안내"가 표시된다. `/projects/:id/result` 는 "임시 화면"이다.

## 6. 2단계에서 이어갈 것
1. `POST /api/projects/:id/renders`(202) 와 `GET /api/renders/:id` 분리. 유니크 인덱스 위반 시 기존 작업 반환
2. 요청 시점 스냅샷 + `render_job_images` 기록, 작업별 폴더에서 ffmpeg 실행(1280×720, 30fps, 무음, libx264)
3. 서버 시작 시 `waiting/generating` → `failed` 처리와 임시 파일 정리
4. Noto Sans KR 글꼴 파일과 OFL 라이선스 전문을 저장소에 포함, 한글 자막 출력 확인
5. 출력 프레임과 미리보기 비교 보고(자막 위치·줄바꿈 차이)
