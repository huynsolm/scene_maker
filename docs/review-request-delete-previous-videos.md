## 1. 무엇을 만들었나
결과 화면에서 **완성된 지난 영상을 하나씩 삭제**한다(실패 기록 삭제·일괄 삭제·자동 삭제는 범위 밖). 삭제는 영상 파일, 작업 기록, **이 영상에만 쓰이던 이전 업로드 이미지**를 함께 지운다. 현재 장면이 쓰거나 다른 작업(진행 중·실패 포함)이 참조하는 이미지는 남긴다.

### 서버 (`c3bc8b9`)
| 파일 | 내용 |
|---|---|
| `server/renderStore.ts` | `listDone`(커서 목록), `deleteVideo`, `recomputeProjectStatus`, `sweepFiles`(실패 허용) |
| `server/store.ts` | `collectImageIfUnused`·`sweepOrphans`를 파일 삭제 실패에도 계속 진행하게 변경 |
| `server/fsSafe.ts` (신규) | `safeRm`(실패 시 경고 로그 후 `false`), `rmdirIfEmpty` |
| `server/app.ts` | `GET /api/projects/:id/renders?limit&before`, `DELETE /api/projects/:id/renders/:jobId` |
| `server/errors.ts`, `shared/types.ts` | `RENDER_NOT_DELETABLE`, `RenderList`/`RenderListItem` |

핵심 규칙
- 삭제 순서: **한 트랜잭션**(연결 이미지 id 읽기 → 작업 행 삭제(연결은 CASCADE) → 프로젝트 상태 재계산) → 커밋 뒤 영상 파일 삭제 → 이미지마다 `collectImageIfUnused`. 파일 삭제 실패는 요청을 실패시키지 않고(로그만), 다음 서버 시작의 `sweepFiles`/`sweepOrphans`가 회수한다.
- `projects.updated_at`은 바꾸지 않는다(바꾸면 남은 영상이 전부 "현재 내용보다 이전"으로 표시됨).
- 목록 정렬 `finished_at DESC, rowid DESC`(= `lastVideo`와 같은 기준), 커서는 `(finished_at, rowid) < (?, ?)`. 기준 영상이 지워졌으면 404.
- 프로젝트 상태 재계산: 활성 작업이 있으면 건드리지 않음. 아니면 **생성 순서상 최신 작업(`created_at DESC, rowid DESC`, 상태 무관)** 의 결과, 단 그 뒤에 내용이 고쳐졌으면 `editing`, 남은 작업이 없으면 `editing`. (완료 A → 실패 B → 완료 C에서 C를 지우면 표시 대체 영상은 A, 프로젝트 상태는 B 기준 `failed`.)
- 다른 프로젝트의 작업 id는 404, 진행 중·실패 작업은 409(`RENDER_NOT_DELETABLE`).

### 화면 (`084e350`)
| 파일 | 내용 |
|---|---|
| `web/screens/PastVideos.tsx` (신규) | 목록(처음 10개+"더 보기"), 삭제 확인 `Modal`, 삭제/재확인 로직 |
| `web/screens/ResultScreen.tsx` | `PastVideos` 배치, 삭제 후 `lastVideo` 재조회(`projectVersion`) |
| `web/api.ts`, `web/styles.css` | `listRenders`/`deleteRender`, 스타일 |

핵심 규칙
- 목록 세대 번호(`gen`): 삭제 성공 시 올려서, 삭제 전에 보낸 목록 응답이 늦게 도착해도 버린다.
- 보고 있던 영상을 지우면 남은 최신 영상으로, 없으면 편집 화면으로 이동. 진행 중 B를 보며 A를 지워도 B의 화면·폴링은 유지.
- 삭제 요청이 **시간 초과 / 연결 끊김(`status 0`)** 이면 "결과 불명": 모든 삭제 버튼을 막고 `[다시 확인]`. **목록 재조회가 성공해야** 진행하고, `getRender(id)`가 404면 삭제됨, 200이면 삭제되지 않음으로 확정. 재조회 실패 시 불명확 유지.
- 404(이미 삭제됨)·409는 안내 후 목록 재조회.
- 계획과 달라진 점: 계획의 `ResultScreen` 세대 번호는 넣지 않았다. `App.tsx`가 `key`로 대상마다 화면을 새로 만들어 늦은 응답이 사라진 화면에만 반영되기 때문(`key`를 빼면 실패하는 E2E로 지킴).

## 3. 특히 봐 주었으면 하는 부분 (스스로 의심하는 곳)
1. **동시성 가정**: `deleteVideo`의 트랜잭션 → 파일 삭제 → 이미지 회수 구간이 동기 실행이라 요청 사이에 끼어들 수 없다는 가정(단일 프로세스, better-sqlite3 동기). 이 가정이 깨지는 경로(예: 렌더 큐가 같은 이미지를 참조하는 새 작업을 만드는 시점과의 순서)가 있는가?
2. **이미지 회수의 정확성**: `collectImageIfUnused`가 "현재 장면 ∪ 남은 모든 작업(활성·실패 포함)이 참조하지 않을 때만" 지우는지, 삭제 직전에 읽은 `imageIds` 이후 새로 참조가 생기는 경우가 없는지.
3. **프로젝트 상태 재계산**이 `finish()`/`createJob()`의 기존 규칙과 모순되지 않는지(특히 `updated_at > created_at` 비교는 문자열 비교이며 같은 시각 동률의 처리).
4. **파일 삭제 실패 정책**: Windows 등에서 `EBUSY/EPERM`일 때 DB는 이미 지워졌으므로 파일은 고아가 된다. 시작 시 정리까지는 남아 있고, 서버를 오래 켜 두면 계속 남는다. 재시도 시점이 시작 시뿐인 것으로 충분한가?
5. **"결과 불명" 처리 범위**: `status 0`(시간 초과뿐 아니라 연결 실패)을 모두 불명확으로 본다. 요청이 서버에 닿지 않은 경우에도 재확인(`getRender`)으로 풀리므로 안전하다고 판단했지만, 놓친 경로가 있는가? `remove`가 404 뒤 목록 재조회에 실패했을 때도 불명확로 보내는 것이 맞는가?
6. **목록 상태**: 삭제 성공 응답은 첫 페이지로 목록을 **덮어쓴다**(이미 "더 보기"로 펼친 항목은 접힌다). 의도적 단순화인데 사용성/정합성 관점에서 문제인가? "더 보기" 중 삭제·삭제 중 "더 보기"의 경쟁은 `gen`과 `moreRef`로 막는다고 보았다.
7. **접근성**: 항목마다 같은 "삭제"/"보기"/"다운로드" 라벨 버튼이 반복된다. 스크린 리더에서 항목을 구분할 `aria-label`이 없다(미적용). 확인 창은 기존 `Modal`(초점 순환·복귀, 기본 초점 취소)을 재사용. 삭제 후 초점이 사라진 버튼 대신 어디로 가는지는 확인하지 않았다.
8. **토스트가 두 곳**(`ResultScreen`·`PastVideos`에 각각 `useToast`)에서 동시에 뜰 수 있다.
9. 다른 탭에서 지워진 영상을 **이미 열어 둔 결과 화면**은(완료 상태는 폴링하지 않아) 재생이 실패할 때까지 알 수 없다. 계획에는 없었으나 허용 가능한가?
10. 목록 쿼리의 `before` 검증(`/^[0-9a-f-]{36}$/`)과 `limit` 범위(1–50)가 충분한가.

### 7.3 특히 봐 주었으면 하는 부분
1. **P2 수정이 모든 경로를 덮는가**: `afterRemoved`에서 `mounted` 확인 뒤 이동한다. `remove`(성공·404 재조회)와 `recheck`가 모두 `afterRemoved`를 거치는데, 이동하지 않는 경로(토스트·`setState`·`loadFirst`)가 언마운트 뒤에도 실행되는 것은 무해하다고 판단했다. 놓친 경로가 있는가?
2. **초점 이동의 빈틈**: 삭제 후 초점을 목록 제목으로 옮기지만, 삭제로 목록이 비면 `PastVideos`가 렌더되지 않아 제목이 없다(예: 진행 중 B를 보며 유일한 완성 영상 A를 삭제). 이때 초점은 문서 맨 앞으로 빠진다 — 알고 있는 빈틈이고 고치지 않았다. 고쳐야 하는가?
3. **접근성 이름**: 버튼 `aria-label`이 "오늘 14:20에 만든 12초 영상 삭제"처럼 눈에 보이는 글자("삭제")를 포함하도록 했다(label-in-name). 같은 분·같은 길이의 영상이 두 개면 이름이 같아진다(E2E는 서로 다른 시각으로만 확인).
4. **`Link` 공용 컴포넌트 변경**: `ariaLabel` 속성을 추가했다(없으면 속성 자체가 렌더되지 않음). 다른 화면에 영향이 없는지.
5. **실측 검사의 독립성(순환성)**: `verify()`가 "필요한 파일"을 DB의 `scenes.image_id`와 `render_job_images`로 계산하는데, 이는 서버의 회수 규칙과 같은 정의다. 서버가 참조를 잘못 이해하면 같은 오해로 통과할 수 있다. 디스크 파일 목록과의 대조(고아 파일, 누락 파일)는 독립이지만 "무엇이 필요한가"의 정의는 독립이 아니다. 이 한계가 수용 가능한가?
6. **측정의 한계**: 4코어 환경 한 곳, 합성 이미지. 실패한 작업 기록이 붙잡는 이미지, Windows 파일 잠금은 측정하지 않았다.

  2. `renders.deleteVideo()` — 트랜잭션(연결 이미지 읽기 → 작업 행 삭제 → 상태 재계산) 커밋 → 영상 파일 삭제 → 이미지 회수. 내부에 `await`이 없다.
  3. `renders.listDone(id, { limit: keep })`로 앞 `keep`개를 읽어 응답한다.
  - 2와 3 사이에 `await`이 없어, 단일 Node 프로세스에서 다른 요청(다른 탭의 삭제, 렌더 완료 콜백)이 끼어들 수 없다. **단, 3은 2의 트랜잭션 안이 아니라 커밋 직후의 별도 조회**다.
- **화면** `keep = min(200, max(10, 펼친 개수 − 1))`을 보내고, 응답의 `list`를 그대로 적용(`apply`)한다. `readRange`·재시도·첫 페이지 비교·`listRenders`의 `limit` 인자는 모두 삭제.

### 17.4 특히 봐 주었으면 하는 부분 (스스로 의심하는 곳)
1. **원자성 전제**: "삭제와 목록 읽기 사이에 끼어들 수 없다"는 단일 프로세스·동기 실행에 기댄다. Fastify 핸들러는 `async`이지만 내부에 `await`이 없다. 렌더 큐의 완료 처리(`finish`)는 ffmpeg 종료 콜백에서 같은 이벤트 루프로 실행되므로 이 구간을 끊지 못한다고 보았다. 이 판단이 맞는가? 목록 읽기를 트랜잭션 안으로 넣어야 할 이유가 있는가(예: 이미지 회수 도중 예외)?
2. **`keep` 계산과 상한**: 화면은 `펼친 개수 − 1`(최소 10, 최대 200)을 보낸다. 200개를 넘게 펼쳤다면 200개로 접힌다(`hasMore`가 나머지를 알림). 200이라는 상한이 적절한가? 응답 크기는 항목당 약 300바이트로 최대 60KB 정도로 보았다.
3. **이전 지적이 정말 닫혔는가**: 시계 역행 중간 삽입(§15 P2), 안쪽 삭제 항목 잔존(§15 P3), 새 영상 누락(§13·§11 P2)이 모두 "응답 하나"라는 구조로 해소된다고 보았다. 단일 응답 이후 새로 완성된 영상이 다음 조회 전까지 안 보이는 것은 일반적인 스냅샷 한계(이전 검수에서 수용)로 남는다.
4. **남은 첫 페이지 접힘 경로**: 404(이미 삭제됨)·재확인(`recheck`)·`RENDER_NOT_DELETABLE` 경로는 여전히 `loadFirst`로 첫 페이지로 접힌다(이전에 수용). 이번 변경과 일관성 면에서 문제가 되는가?
5. **API 호환**: `keep`을 생략하면 기존처럼 10개다. 이 API를 쓰는 곳은 `PastVideos` 하나뿐이다.
6. **입력 검증 경계**(임시 테스트로 확인): `keep=`(빈 값)·`keep=10&keep=20`(중복)·`keep=%20`(공백)은 모두 400. 반면 `keep=1e1`은 `Number('1e1') = 10`으로 해석돼 **200으로 처리**된다(같은 이유로 `0x10`은 16으로 받아들여질 것으로 보이나 미확인). 값이 1~200 범위 안이면 결과는 무해하다고 보아 막지 않았다 — 엄격히 10진 정수만 받아야 하는가?

## 19. 남은 한계 정리 (PR #8 병합 뒤)
PR #8 본문의 "알려진 한계" 가운데 사용자가 실제로 겪는 불편을 고치고, 나머지는 그대로 두는 이유를 기록한다.

| 한계 | 처리 |
|---|---|
| 목록을 다시 읽는 경로(보던 작업 완성, 이미 삭제된 영상 404, 삭제 불가 409, 결과 재확인, "더 보기" 기준 소실)에서 펼친 목록이 첫 페이지(10개)로 접힘 | **개선.** `loadFirst`가 지금 펼친 개수(최소 10, 최대 200)만큼 한 번의 요청으로 읽는다. 이를 위해 `GET /renders`의 `limit` 상한을 50 → 200으로 올려 삭제 응답(`keep`)의 상한과 맞췄다. E2E 2개(404 뒤 펼친 목록 유지 / 보던 작업 완성 뒤 펼친 목록 유지), API 상한 검사(201은 400, 200은 허용). 다시 읽을 때 항상 10개만 읽게 하면 두 E2E가, 서버 상한을 50으로 되돌리면 API 테스트가 실패함을 확인 |
| 200편 넘게 펼친 상태에서 삭제·재조회하면 200편으로 접힘 | 유지. 단일 사용자 앱에서 드물고, 접혀도 "더 보기"로 모두 읽을 수 있다(데이터 누락 아님) |
| 응답 이후 새로 완성된 영상은 다음 조회 때 나타남 | 유지. 모든 목록 조회의 스냅샷 한계(코덱스 수용) |
| `keep`·`limit`이 `1e1`·`0x10` 표기를 숫자로 받아들임 | 유지. 범위 검증이 있어 무해(코덱스 수용) |
| 정합성 보장이 단일 Node 프로세스·동기 SQLite 전제 | 유지. 아키텍처 변경이라 범위 밖 |
| 실패한 작업 기록이 붙잡는 이미지는 회수되지 않음 | 유지. "실패 기록 삭제는 범위 밖"은 사용자 결정 — 바꾸려면 별도 결정이 필요 |
