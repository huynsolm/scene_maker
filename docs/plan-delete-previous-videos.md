# 계획: 이전 영상 개별 삭제

상태: **1단계(서버)·2단계(결과 화면 UI)·3단계(디스크 실측) 구현 완료**. Codex 계획 검수의 권고를 반영했다(§8). 기준 코드: `main` 3949e0d.

## 1. 목적과 배경
디스크 측정(`docs/disk-usage.md`)에서, 이미지를 바꿔 영상을 다시 만들 때마다 약 17MB(휴대폰 사진 3장 교체 + 새 영상 2.7MB)가 상한 없이 쌓였다. 원인은 기존 결정의 조합이다. 영상을 자동 삭제하지 않고, 이미지는 어떤 장면과 어떤 작업도 참조하지 않을 때만 지운다. 사용자가 지난 영상을 **직접** 지울 수 있게 해서 누적을 줄인다. 자동 삭제 규칙은 바꾸지 않는다. 회수량은 공유 참조에 따라 달라지므로 "삭제 한 건에 17MB 회수"를 약속하지 않는다.

## 2. 현재 구조(계획의 전제)
- 영상 하나 = `render_jobs` 행 + 영상 파일(`videos/<프로젝트>/<작업>.mp4`) + `render_job_images` 연결(`createJob`이 같은 트랜잭션에서 INSERT, `job_id`는 `ON DELETE CASCADE`).
- `Store.collectImageIfUnused`: 어떤 장면과 어떤 작업도 참조하지 않을 때만 이미지 행과 파일을 지운다. **DB 행을 지운 뒤 `fs.rmSync(…, { force: true })`를 호출한다.** `force`는 "없는 파일"만 무시하므로 잠금·권한 오류는 그대로 던져진다.
- 서버 시작(`server/app.ts`): `failInterrupted → sweepFiles → sweepOrphans`가 예외 처리 없이 호출된다. 두 정리 함수의 `rmSync`도 오류를 던질 수 있다.
- `Store.getProject().lastVideo` = `status='done' AND video_file IS NOT NULL` 중 `finished_at DESC, rowid DESC` 첫 번째.
- `RenderStore.latestForProject` = **상태와 무관한** 가장 최근 작업(`created_at DESC, rowid DESC`). 실패·진행 중도 반환한다.
- 지난 영상 목록 API/화면은 없다. `ResultScreen.load`는 응답이 어느 대상의 것인지 구분하지 않는다.

## 3. 확정한 결정
| 항목 | 결정 |
|---|---|
| 목록 위치 | 결과 화면 안의 "이전에 만든 영상" 섹션. **처음부터 개수를 제한하고 "더 보기"를 둔다** |
| 삭제 대상 | **완성된 영상만.** 실패 기록은 범위 밖(실패 후 이미지 교체로 쌓이는 경로는 그대로) |
| 삭제 방식 | **개별 삭제만.** 일괄 삭제는 필요해지면 나중에 |
| 자동 삭제 | 없음. 확인 창을 거친 사용자 삭제만 |
| 파일 크기 표시 | 후속 |

## 4. 서버

### 4.1 정렬 규칙(동률 포함, 두 가지를 구분한다)
| 용도 | 정렬 | 이유 |
|---|---|---|
| 목록, 대체로 보여 줄 영상 | `finished_at DESC, rowid DESC`, 완료·`video_file` 있음만 | 기존 `lastVideo`와 같다. 같은 시각이면 `rowid`가 큰 쪽이 먼저 |
| 프로젝트 상태 재계산의 기준 작업 | `created_at DESC, rowid DESC`, 상태 무관 | 기존 `latestForProject`/`finish`와 같다 |

"남은 최신 완성 영상"을 찾는 데 `latestForProject`를 쓰지 않는다.

### 4.2 목록
`GET /api/projects/:id/renders?limit=&before=`
- 완성된 영상만. 기본 `limit` 10, 최대 50. `before`는 직전 페이지의 마지막 항목 id(위 정렬의 다음 항목부터). 응답: `items`, `hasMore`, `total`.
- 항목: `id`, `createdAt`, `finishedAt`, `totalSec`, `sceneCount`, `outdated`(기존 `toView`와 같은 정의), `videoUrl`, `downloadUrl`.
- 프로젝트가 없으면 404. `before`가 없는(이미 지워진) 항목이면 첫 페이지부터 다시 읽도록 안내하는 오류(400/404, 구현 때 정한다).

### 4.3 삭제
`DELETE /api/projects/:id/renders/:jobId`
1. 프로젝트 소속 검증(다른 프로젝트의 작업이면 404). 없는 작업(이미 지움 포함) 404.
2. 활성(`waiting`/`generating`)이면 409. 완료가 아니면(실패 기록) 거절.
3. **한 트랜잭션**: 대상 작업의 연결 이미지 id 목록을 읽음 → 작업 행 삭제(연결은 CASCADE) → 프로젝트 상태 재계산. **`projects.updated_at`은 바꾸지 않는다**(삭제는 편집 내용의 변경이 아니다. 바꾸면 남은 영상이 모두 `outdated`로 표시된다).
4. **트랜잭션 커밋 뒤**의 파일 정리는 각각 실패해도 계속 진행한다(§4.4).
5. 응답: 갱신된 목록 첫 페이지와 `lastVideo`(구현 때 확정). 같은 삭제를 다시 호출하면 404.

### 4.4 파일 삭제 실패 정책(DB 커밋 이후)
- 영상 파일과 이미지 파일 삭제를 **각각** 시도하고, 하나가 실패해도 나머지를 계속한다. 하나의 이미지 정리 실패가 다른 이미지 회수를 막지 않는다.
- 실패한 경로와 오류 코드를 로그로 남기고, 삭제 응답은 성공으로 돌려준다(기록은 이미 사라졌다). 회수는 다음 서버 시작 때 이루어진다.
- **잡는 것은 파일 시스템 오류뿐**이다. DB 오류까지 일괄 무시하지 않는다.
- `collectImageIfUnused`가 파일 삭제 오류를 던지던 것을 같은 정책으로 바꾼다(DB 행 삭제 뒤 파일 삭제 실패는 기록하고 `true` 반환). 이 함수를 쓰는 기존 호출(이미지 교체·삭제, 장면 삭제)도 같은 이유로 500을 돌려주던 것이 사라진다. 영향 범위를 테스트로 확인한다.
- **시작 시 정리(`sweepFiles`, `sweepOrphans`)**: 파일마다 `try/catch`로 실패를 기록하고 건너뛴다. 잠긴 파일 하나 때문에 서버 시작 전체가 실패하지 않으며, 다음 시작 때 다시 시도한다. 반환값에 실패 개수를 포함한다.

### 4.5 프로젝트 상태 재계산
활성 작업이 있으면 건드리지 않는다. 아니면 남은 작업 중 생성 순서상 최신 것(§4.1 두 번째 행)을 기준으로 결과(done/failed)를 쓰되, `projects.updated_at > 그 작업.created_at`이면 `editing`(기존 `finish`와 같은 규칙). 남은 작업이 없으면 `editing`.

### 4.6 동시성 가정
서버는 단일 프로세스이고 `better-sqlite3`와 위 구간이 모두 동기 실행이라 트랜잭션·이미지 회수 사이에 다른 요청이 끼어들지 않는다. 향후 파일 작업을 비동기로 바꾸면 이 가정을 다시 검토해야 한다.

## 5. 화면

### 5.1 목록과 삭제
- 결과 화면에 "이전에 만든 영상": 생성 시각, 길이, 장면 수, "현재 내용보다 이전" 표시, 보기·다운로드·삭제. 처음 10개와 "더 보기". 현재 보고 있는 영상은 표시한다.
- 삭제 확인 창(기존 `Modal`: 초점 순환·복귀): "이 영상을 삭제할까요? 영상 파일이 지워지고 되돌릴 수 없어요. 이 영상에만 쓰인 이전 이미지도 함께 지워져요. 지금 편집 중인 내용에는 영향이 없어요." 기본 초점은 취소.

### 5.2 응답 무효화와 대상 전환(검수 반영)
- (구현 메모) 보는 작업이 바뀌면 `App`이 `key`로 `ResultScreen`을 새로 만들기 때문에 이전 작업의 조회·폴링 응답은 사라진 화면에만 반영된다 — 별도 세대 번호는 필요 없다(`key`를 빼면 실패하는 E2E로 지킨다). 목록은 `PastVideos`가 자기 세대 번호를 가진다.
- (계획 원문) `ResultScreen.load`에 **세대 번호**를 둔다. 보는 대상(`projectId`/`jobId`)이 바뀌거나 삭제로 대상이 바뀌면 세대를 올리고, 이전 세대의 조회·폴링 응답은 버린다. 목록 조회도 자기 세대를 따로 가진다.
- **진행 중 작업 B를 보는 동안 이전 영상 A를 삭제해도 B의 선택과 폴링은 유지**한다. 삭제는 목록 상태만 갱신하고 보고 있는 작업 상태(`job`)를 건드리지 않는다.
- **보고 있던 영상을 지운 경우**: 새로 읽은 목록의 첫 항목(§4.1 첫 행 정렬)으로 이동하고, 없으면 편집 화면으로 이동한다. `latestForProject`에 의존하지 않는다.
- **삭제가 시간 초과**(`TIMEOUT`)되면 결과를 알 수 없다: 모든 삭제 버튼을 비활성화하고 "삭제 결과를 확인하지 못했어요 [다시 확인]"을 보인다. **목록 재조회가 성공해야** 상태를 확정하고(항목이 사라졌으면 삭제됨, 남아 있으면 삭제되지 않음) 버튼을 푼다. 재조회도 실패하면 불명확 상태를 유지한다. `docs/request-timeout.md`의 장면 추가·삭제 `'unknown'` 원칙과 같다.
- 다른 화면에서 같은 영상을 이미 지웠다면(404) 목록을 다시 읽고 이미 지워졌다고 안내한다.
- 편집 화면의 "마지막 생성 영상 보기"와 프로젝트 목록의 상태는 삭제 후 다시 불러와 갱신한다.

## 6. 검증 계획

### 6.1 API 테스트
- 완료 영상 삭제 → 행·파일·연결 삭제, 이 영상에만 쓰인 이미지 회수, **현재 장면 이미지와 다른 작업(활성·실패 포함)이 공유하는 이미지는 보존**
- 진행 중 409 / 다른 프로젝트 404 / 이미 지운 영상 404 / 실패 기록 삭제 거절
- 프로젝트 상태 재계산: 마지막 영상 삭제, 오래된 영상만 남음(`outdated`), 영상 없음, 활성 작업 동시 존재. **`updated_at` 불변**
- **완료 A → 실패 B → 완료 C에서 C 삭제**: 표시 대상은 A, 프로젝트 상태는 B 기준
- **같은 시각의 작업들**: 목록·대체 영상·상태 계산의 정렬 동률(`rowid`)
- 목록: 제한과 `before` 커서, `hasMore`/`total`, 삭제로 커서 대상이 사라진 경우
- **파일 삭제 실패 주입**(`fs.rmSync`를 특정 경로에서 던지게 함): 영상 파일 실패, 이미지 파일 실패를 각각 → 삭제 응답 성공, 나머지 정리 계속 진행, 로그 기록, **재시작(`sweepFiles`/`sweepOrphans`) 후 회수**, 시작 정리에서 여전히 잠긴 파일이 있어도 서버 시작이 실패하지 않음
- **삭제 직후 프로세스 중단**: 트랜잭션 뒤·파일 삭제 전을 흉내 내(파일을 남긴 채 DB만 삭제 상태) 재시작 후 고아 영상·이미지 회수
- 이전 완료 영상 삭제 + 다른 작업 생성 중: 상태·진행·공유 이미지 보존

### 6.2 E2E
- 목록 표시와 "더 보기", 확인 창 취소는 아무것도 지우지 않음, 삭제 후 목록·"마지막 생성 영상 보기" 갱신
- 보고 있던 영상 삭제 후 이동(남은 최신, 없으면 편집 화면), 삭제된 영상 주소는 "찾을 수 없음"
- 진행 중 B를 보며 A 삭제: B의 선택·폴링 유지
- **지연된 조회 응답**: 삭제 전에 보낸 조회가 늦게 도착해도 삭제된 항목이 되살아나지 않음
- **다른 화면에서의 중복 삭제**(404), **삭제 시간 초과**(버튼 비활성화 → 재조회 성공 후 확정, 재조회 실패 시 유지)

### 6.3 변이 검사
이미지 회수 호출 제거, 소속 검증 제거, 활성 검사 제거, 상태 재계산 제거, 세대 검사 제거, 파일 삭제 오류 처리 제거가 각각 대응 테스트를 실패시키는지. 변이는 빌드 성공을 확인한 뒤에만 테스트를 돌린다.

### 6.4 실측
`npm run measure:disk`에 "오래된 완료 영상을 모두 삭제한 뒤" 단계를 더한다. 회수량의 크기를 단정하지 않고, **삭제 뒤 남은 파일이 현재 장면과 남은 작업이 필요로 하는 파일(업로드 이미지 = 장면 참조 ∪ 남은 작업 참조, 영상 = 남은 작업의 영상)과 정확히 일치**하는지를 확인한다.

## 7. 위험과 한계
- 삭제는 되돌릴 수 없다(확인 창으로 완화).
- Windows에서 다운로드·재생 중인 영상은 파일 삭제가 잠금으로 실패할 수 있다. 기록은 사라지고 파일은 다음 서버 시작 때 지워진다(지연 있음).
- 실패 기록이 붙잡는 이미지는 회수 대상이 아니다.
- 서버가 트랜잭션 직후·파일 삭제 전에 멈추면 고아 파일이 남지만 시작 시 정리가 지운다.
