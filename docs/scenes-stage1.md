# 후속 기능: 장면 수 가변 — 1단계(서버)

장면을 3개 고정에서 **1~10개**로 바꾸는 작업의 서버 쪽이다. 화면(추가·삭제 버튼, 문구 정리)은 2단계에서 한다. 이 단계의 화면 변경은 기존 편집 화면이 새 API 로 계속 동작하게 하는 최소한뿐이다.

## 사용자 결정
- 장면 수 **최소 1 ~ 최대 10**, 새 프로젝트 기본 **3개**, 총 길이 상한 **300초**.
- 총 길이 300초는 장면 10개 x 30초와 같아서 별도 검사를 두지 않았다. 두 한도가 이미 보장한다(`TOTAL_MAX_SEC = SCENE_MAX * DURATION_MAX_SEC`). 한도를 바꿀 때는 이 관계를 다시 봐야 한다.
- 순서 변경은 범위 밖이다(복잡한 타임라인 제외 원칙).

## 설계
| 항목 | 내용 |
|---|---|
| 장면 식별 | 장면마다 UUID(`scenes.id`). 이미지 업로드·삭제 경로가 `/api/projects/:id/scenes/:sceneId/image` 로 바뀌었다 |
| 순서 | `position` 은 표시 순서이며 트랜잭션 안에서 0..n-1 로 유지한다. 유니크 제약은 두지 않았다(한 칸씩 당길 때 일시적으로 충돌하기 때문) |
| 추가 | `POST /api/projects/:id/scenes` → 맨 뒤에 빈 장면(길이 10초). 최대 개수에서 `SCENE_LIMIT`(422) |
| 삭제 | `DELETE /api/projects/:id/scenes/:sceneId`. 마지막 한 장면은 `SCENE_MIN`(422), 없는 장면은 404. 뒤 장면 순서를 당기고, 이미지는 장면·렌더 작업 어디에서도 쓰지 않을 때만 정리 |
| 저장 | 본문에 장면 ID 를 담으면 서버의 현재 장면 목록(순서 포함)과 같아야 한다. 다르면 `SCENES_CHANGED`(409). 추가·삭제 전에 보낸 오래된 저장이 삭제된 장면을 되살리지 못한다 |
| ID 없는 저장 | 내부 호출·하위 호환용. 현재 장면 수와 같을 때 위치 순서로 적용, 다르면 409. ID 를 일부만 보내면 400 |
| 이전(migration) | 옛 `scenes` 표(PRIMARY KEY (project_id, position), position 0..2 CHECK)를 한 트랜잭션에서 새 표로 옮긴다. 행·순서·이미지 연결을 보존하고 ID 만 새로 붙는다. 실패하면 이전 표가 그대로 남는다 |
| 렌더 | 렌더러·스냅샷·결과 화면은 이미 장면 배열 기반이라 코드 변경이 없다. 1개·5개 장면을 실제 ffmpeg 로 만들어 길이와 전환 시각을 검증한다 |

## 검증 (Node 22.23.4)
- 타입체크 통과, 단위·API·ffmpeg 133개, E2E 37개 통과(검수 반영 전)
- 신규 `tests/scenes.test.ts`(10개): 기본 ID·순서, 추가·최대, 중간 삭제 시 내용·이미지 이동, 최소·404, 이미지 정리, 오래된 저장 거절(삭제·추가 양쪽), ID 일부·순서 불일치, 다른 프로젝트의 장면 ID, 장면 수가 바뀐 프로젝트의 스냅샷
- `tests/migrate.test.ts`(+1): 옛 표 이전 시 내용·순서·이미지 연결 보존, ID 고유, 임시 표 미잔존, CHECK 해제, CASCADE 유지, 재실행 시 ID 불변
- `tests/ffmpeg.test.ts`(+1): 장면 1개(4초), 5개(18초, 전환 3·7·10·15초) 실제 렌더
- 변이 검사: 장면 목록 일치 검사를 제거하면 오래된 저장 관련 3개 테스트가 실패(확인 후 원복)

## 확인하지 못한 것 / 다음 단계
- 편집 화면에는 아직 추가·삭제 UI 가 없다(2단계). 현재 화면은 서버의 장면 ID 를 저장 본문에 실어 보내고, 이미지 API 에 ID 를 쓴다.
- 자동 저장이 409 를 받았을 때 화면이 어떻게 복구할지(새로 고침 안내)는 2단계에서 정한다.
- 대용량 이미지 10장의 렌더 시간·디스크 사용량은 측정하지 않았다.

## 검수 후속 (P2 2건)

| # | 지적 | 판단 | 처리 |
|---|---|---|---|
| P2-1 | 실제 장면 수보다 큰 `?scene=` 값(기본 3장면에서 `?scene=4`)으로 열면 `scenes[sel]` 이 없어 편집 화면이 예외로 깨진다. 결과 화면의 장면 링크도 장면을 지운 뒤에는 범위를 벗어난다 | 타당(가변 장면으로 새로 생긴 결함. 이전에는 3 이하로 고정이라 범위 검사만으로 충분했다) | 선택값을 항상 실제 장면 수 안으로 맞춘다(`sel = min(선택값, 장면 수 - 1)`). 범위를 넘으면 마지막 장면이 선택된다. E2E(`?scene=4`, `?scene=10`, 페이지 오류 없음) 추가 |
| P2-2 | 업로드·삭제 응답을 배열 위치로 합쳐서, 화면 `[A,B,C]` 에서 다른 요청이 A 를 지운 뒤 B 에 업로드하면 화면의 B 에 C 의 이미지가 표시된다 | 타당 | `web/mergeImages.ts` 로 **장면 ID 로** 합친다. 응답에 없는 장면(다른 곳에서 지워진)은 그대로 둔다. 단위 테스트 3개(검수 반례 포함) |

- **검증**: 단위 136개, E2E 38개 통과(Node 22.23.4). `?scene=` 보정을 빼면 신규 E2E 가 실패한다(확인 후 원복).
- **문서에 덧붙이는 한계(검수 제안)**: 장면 ID 없이 보내는 저장은 호환 경로라, 삭제 뒤 추가로 장면 수가 다시 같아지면 오래된 저장을 감지하지 못한다. 웹 화면은 항상 ID 를 보내므로 이 경로에 해당하지 않는다.
- **2단계에서 다룰 것**: 업로드 중 표시(`uploading`)가 아직 위치 기준이라 장면이 지워지면 잠시 다른 장면에 표시될 수 있다. 화면의 장면 구성이 서버와 달라졌을 때(저장 409)의 복구 안내. `ConfirmModal` 과 목록 카드의 "장면 3개" 문구.

# 장면 수 가변 — 2단계(편집 화면)

장면 추가·삭제 UI 와 충돌 복구, 남아 있던 "장면 3개" 문구 정리.

## 동작
| 항목 | 내용 |
|---|---|
| 추가 | 장면 목록 아래 "+ 장면 추가". 새 장면이 선택된다. 10개가 되면 "장면은 최대 10개예요"로 막힌다 |
| 삭제 | 선택한 장면의 편집 패널 위쪽 "장면 삭제" → 확인 창(문구·길이·이미지가 지워지고 되돌릴 수 없으며 이미 만든 영상에는 영향 없음). 장면이 1개면 막힌다 |
| 저장과의 순서 | 추가·삭제 전에 대기 중인 입력을 먼저 저장하고, 진행하는 동안 자동 저장은 끝나기를 기다렸다가 새 장면 ID 로 나간다. 서버가 돌려준 장면 목록을 draft 에 합칠 때 같은 ID 의 장면은 화면의 문구·길이를 유지한다 |
| 충돌(저장 409, 삭제 시 404) | 빨간 안내 띠 "장면 구성이 다른 곳에서 바뀌어서 저장할 수 없어요… 새로 불러오기". 새로 불러오면 이 화면의 저장되지 않은 수정은 사라진다고 미리 알린다 |
| 선택 번호 | 항상 실제 장면 수 안으로 맞춘다. 지우면 그 자리의 다음 장면(없으면 마지막)이 선택된다 |
| 이미지 연결 | 화면의 장면 이미지를 위치가 아니라 장면 ID 로 맞춘다. 업로드 중 표시도 장면 ID 기준이라 장면이 지워져도 다른 장면에 표시되지 않는다 |
| 문구 | 목록 카드 "장면 N개 · T초"(서버 `sceneCount`), 빈 목록 안내, 영상 만들기 확인 창의 장면 수, 전체 길이 안내를 장면 수에 맞춤 |

## 검증 (Node 22.23.4)
- 타입체크 통과, 단위·API·ffmpeg 137개, E2E 43개 통과
- E2E 신규 5개: 추가(선택·새로고침 뒤 유지), 최대 10개와 최소 1개 막힘, 삭제 확인 취소·내용 당겨짐·삭제 직전 입력 보존, 목록 카드 장면 수, 두 화면 충돌(지운 장면이 되살아나지 않음, 새로 불러오기)
- 단위 신규 1개: 목록의 `sceneCount`·`totalSec`
- 변이 검사: 추가·삭제 전 저장(flush)을 빼면 "삭제 직전 입력 보존" E2E 가 실패한다(확인 후 원복)

## 확인하지 못한 것
- 좁은 화면(390px·320px)의 편집 화면 배치는 확인하지 않았다(결과 화면만 기존 E2E 가 있다). 장면 10개일 때 왼쪽 목록은 스크롤된다.
- 순서 변경은 만들지 않았다(범위 밖). 장면 중간에 끼워 넣기도 없다(맨 뒤에만 추가).
- 실제 사용자가 장면 10개로 만든 영상의 렌더 시간·디스크 사용량은 측정하지 않았다.
