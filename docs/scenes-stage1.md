# 후속 기능: 장면 수 가변 — 1단계(서버)

장면을 3개 고정에서 **1~10개**로 바꾸는 작업의 서버 쪽이다. 화면(추가·삭제 버튼, 문구 정리)은 2단계에서 한다. 이 단계의 화면 변경은 기존 편집 화면이 새 API 로 계속 동작하게 하는 최소한뿐이다.

## 사용자 결정
- 장면 수 **최소 1 ~ 최대 10**, 새 프로젝트 기본 **3개**, 총 길이 상한 **300초**.
- 총 길이 300초는 장면 10개 x 30초와 같아서 별도 검사를 두지 않았다. 두 한도가 이미 보장한다(`TOTAL_MAX_SEC = SCENE_MAX * DURATION_MAX_SEC`). 한도를 바꿀 때는 이 관계를 다시 봐야 한다.
- 순서 변경은 범위 밖이다(복잡한 타임라인 제외 원칙).

## 설계
| 항목 | 내용 |
|---|---|
| 장면 식별 | 장면마다 UUID(`scenes.id`). 이미지 업로드·삭제 경로가 `/api/projects/:id/scenes/:sceneId/image` 로 바뀌었다 |
| 순서 | `position` 은 표시 순서이며 트랜잭션 안에서 0..n-1 로 유지한다. 유니크 제약은 두지 않았다(한 칸씩 당길 때 일시적으로 충돌하기 때문) |
| 추가 | `POST /api/projects/:id/scenes` → 맨 뒤에 빈 장면(길이 10초). 최대 개수에서 `SCENE_LIMIT`(422) |
| 삭제 | `DELETE /api/projects/:id/scenes/:sceneId`. 마지막 한 장면은 `SCENE_MIN`(422), 없는 장면은 404. 뒤 장면 순서를 당기고, 이미지는 장면·렌더 작업 어디에서도 쓰지 않을 때만 정리 |
| 저장 | 본문에 장면 ID 를 담으면 서버의 현재 장면 목록(순서 포함)과 같아야 한다. 다르면 `SCENES_CHANGED`(409). 추가·삭제 전에 보낸 오래된 저장이 삭제된 장면을 되살리지 못한다 |
| ID 없는 저장 | 내부 호출·하위 호환용. 현재 장면 수와 같을 때 위치 순서로 적용, 다르면 409. ID 를 일부만 보내면 400 |
| 이전(migration) | 옛 `scenes` 표(PRIMARY KEY (project_id, position), position 0..2 CHECK)를 한 트랜잭션에서 새 표로 옮긴다. 행·순서·이미지 연결을 보존하고 ID 만 새로 붙는다. 실패하면 이전 표가 그대로 남는다 |
| 렌더 | 렌더러·스냅샷·결과 화면은 이미 장면 배열 기반이라 코드 변경이 없다. 1개·5개 장면을 실제 ffmpeg 로 만들어 길이와 전환 시각을 검증한다 |

## 검증 (Node 22.23.4)
- 타입체크 통과, 단위·API·ffmpeg 133개, E2E 37개 통과(검수 반영 전)
- 신규 `tests/scenes.test.ts`(10개): 기본 ID·순서, 추가·최대, 중간 삭제 시 내용·이미지 이동, 최소·404, 이미지 정리, 오래된 저장 거절(삭제·추가 양쪽), ID 일부·순서 불일치, 다른 프로젝트의 장면 ID, 장면 수가 바뀐 프로젝트의 스냅샷
- `tests/migrate.test.ts`(+1): 옛 표 이전 시 내용·순서·이미지 연결 보존, ID 고유, 임시 표 미잔존, CHECK 해제, CASCADE 유지, 재실행 시 ID 불변
- `tests/ffmpeg.test.ts`(+1): 장면 1개(4초), 5개(18초, 전환 3·7·10·15초) 실제 렌더
- 변이 검사: 장면 목록 일치 검사를 제거하면 오래된 저장 관련 3개 테스트가 실패(확인 후 원복)

## 확인하지 못한 것 / 다음 단계
- 편집 화면에는 아직 추가·삭제 UI 가 없다(2단계). 현재 화면은 서버의 장면 ID 를 저장 본문에 실어 보내고, 이미지 API 에 ID 를 쓴다.
- 자동 저장이 409 를 받았을 때 화면이 어떻게 복구할지(새로 고침 안내)는 2단계에서 정한다.
- 대용량 이미지 10장의 렌더 시간·디스크 사용량은 측정하지 않았다.

## 검수 후속 (P2 2건)

| # | 지적 | 판단 | 처리 |
|---|---|---|---|
| P2-1 | 실제 장면 수보다 큰 `?scene=` 값(기본 3장면에서 `?scene=4`)으로 열면 `scenes[sel]` 이 없어 편집 화면이 예외로 깨진다. 결과 화면의 장면 링크도 장면을 지운 뒤에는 범위를 벗어난다 | 타당(가변 장면으로 새로 생긴 결함. 이전에는 3 이하로 고정이라 범위 검사만으로 충분했다) | 선택값을 항상 실제 장면 수 안으로 맞춘다(`sel = min(선택값, 장면 수 - 1)`). 범위를 넘으면 마지막 장면이 선택된다. E2E(`?scene=4`, `?scene=10`, 페이지 오류 없음) 추가 |
| P2-2 | 업로드·삭제 응답을 배열 위치로 합쳐서, 화면 `[A,B,C]` 에서 다른 요청이 A 를 지운 뒤 B 에 업로드하면 화면의 B 에 C 의 이미지가 표시된다 | 타당 | `web/mergeImages.ts` 로 **장면 ID 로** 합친다. 응답에 없는 장면(다른 곳에서 지워진)은 그대로 둔다. 단위 테스트 3개(검수 반례 포함) |

- **검증**: 단위 136개, E2E 38개 통과(Node 22.23.4). `?scene=` 보정을 빼면 신규 E2E 가 실패한다(확인 후 원복).
- **문서에 덧붙이는 한계(검수 제안)**: 장면 ID 없이 보내는 저장은 호환 경로라, 삭제 뒤 추가로 장면 수가 다시 같아지면 오래된 저장을 감지하지 못한다. 웹 화면은 항상 ID 를 보내므로 이 경로에 해당하지 않는다.
- **2단계에서 다룰 것**: 업로드 중 표시(`uploading`)가 아직 위치 기준이라 장면이 지워지면 잠시 다른 장면에 표시될 수 있다. 화면의 장면 구성이 서버와 달라졌을 때(저장 409)의 복구 안내. `ConfirmModal` 과 목록 카드의 "장면 3개" 문구.

# 장면 수 가변 — 2단계(편집 화면)

장면 추가·삭제 UI 와 충돌 복구, 남아 있던 "장면 3개" 문구 정리.

## 동작
| 항목 | 내용 |
|---|---|
| 추가 | 장면 목록 아래 "+ 장면 추가". 새 장면이 선택된다. 10개가 되면 "장면은 최대 10개예요"로 막힌다 |
| 삭제 | 선택한 장면의 편집 패널 위쪽 "장면 삭제" → 확인 창(문구·길이·이미지가 지워지고 되돌릴 수 없으며 이미 만든 영상에는 영향 없음). 장면이 1개면 막힌다 |
| 저장과의 순서 | 추가·삭제 전에 대기 중인 입력을 먼저 저장하고, 진행하는 동안 자동 저장은 끝나기를 기다렸다가 새 장면 ID 로 나간다. 서버가 돌려준 장면 목록을 draft 에 합칠 때 같은 ID 의 장면은 화면의 문구·길이를 유지한다 |
| 충돌(저장 409, 삭제 시 404) | 빨간 안내 띠 "장면 구성이 다른 곳에서 바뀌어서 저장할 수 없어요… 새로 불러오기". 새로 불러오면 이 화면의 저장되지 않은 수정은 사라진다고 미리 알린다 |
| 선택 번호 | 항상 실제 장면 수 안으로 맞춘다. 지우면 그 자리의 다음 장면(없으면 마지막)이 선택된다 |
| 이미지 연결 | 화면의 장면 이미지를 위치가 아니라 장면 ID 로 맞춘다. 업로드 중 표시도 장면 ID 기준이라 장면이 지워져도 다른 장면에 표시되지 않는다 |
| 문구 | 목록 카드 "장면 N개 · T초"(서버 `sceneCount`), 빈 목록 안내, 영상 만들기 확인 창의 장면 수, 전체 길이 안내를 장면 수에 맞춤 |

## 검증 (Node 22.23.4)
- 타입체크 통과, 단위·API·ffmpeg 137개, E2E 43개 통과(검수 반영 전)
- E2E 신규 5개: 추가(선택·새로고침 뒤 유지), 최대 10개와 최소 1개 막힘, 삭제 확인 취소·내용 당겨짐·삭제 직전 입력 보존, 목록 카드 장면 수, 두 화면 충돌(지운 장면이 되살아나지 않음, 새로 불러오기)
- 단위 신규 1개: 목록의 `sceneCount`·`totalSec`
- 변이 검사: 추가·삭제 전 저장(flush)을 빼면 "삭제 직전 입력 보존" E2E 가 실패한다(확인 후 원복)

## 확인하지 못한 것
- 좁은 화면(390px·320px)의 편집 화면 배치는 확인하지 않았다(결과 화면만 기존 E2E 가 있다). 장면 10개일 때 왼쪽 목록은 스크롤된다.
- 순서 변경은 만들지 않았다(범위 밖). 장면 중간에 끼워 넣기도 없다(맨 뒤에만 추가).
- 실제 사용자가 장면 10개로 만든 영상의 렌더 시간·디스크 사용량은 측정하지 않았다.

## 2단계 검수 후속 (P2 4건)

| # | 지적 | 판단 | 처리 |
|---|---|---|---|
| P2-1 | 장면 추가·삭제가 진행 중일 때 영상 생성이 먼저 실행됨(`saveNow` 가 보낼 저장이 없으면 바로 통과해, 서버가 추가·삭제를 끝내기 전에 요청이 나간다. 업로드 중에 눌러도 이전 이미지로 만들어진다) | 타당 | 서버를 바꾸는 요청(업로드·이미지 삭제·장면 추가·삭제)을 **한 줄(`enqueue`)** 로 세우고, `saveNow` 는 줄이 비기를 기다린 뒤 저장한다. 장면을 바꾸는 중에는 "영상 만들기" 버튼을 비활성화하고 시작 함수도 막는다 |
| P2-2 | 늦게 도착한 구조 변경 응답이 그 사이 올린 이미지의 표시를 덮음(서버는 추가를 먼저 처리했지만 응답이 업로드 응답보다 늦게 도착하면 오래된 목록으로 `setProject` 함) | 타당 | 같은 줄 세우기로 응답 도착 순서가 요청 순서와 같아진다. 업로드는 이제 순서대로 처리된다(동시 업로드 없음) |
| P2-3 | 새로 불러온 뒤 이전 저장의 409 응답이 충돌 안내를 다시 켬 | 타당 | `load()` 마다 세대 번호를 올리고, 이전 세대에서 보낸 저장·업로드·장면 변경의 응답(성공이든 실패든)은 새 화면에 반영하지 않는다. 성공 응답이 새로 불러온 뒤의 `savedVersion` 을 흐트러뜨리는 경로도 같이 막힌다 |
| P2-4 | 삭제 확인 창의 키보드 초점 순환·복귀 누락 | 타당 | `Modal`(`web/components.tsx`) 공통 수정: 열릴 때 `data-autofocus`(없으면 첫 요소)로 초점, Tab/Shift+Tab 이 창 안에서만 순환, 닫히면 열기 전 요소로 복귀(쓸 수 없으면 선택된 장면 카드). 열고 닫는 효과가 부모의 렌더마다 다시 실행되던 것도 ref 로 고쳤다. 영상 만들기 확인 창·프로젝트 삭제 창에도 적용된다 |

- **검증**: 타입체크 통과, 단위·API·ffmpeg 137개, E2E 48개 통과(신규 5개). 각 지적마다 E2E 1개씩이며, 변이 검사로 대응하는 테스트만 실패하는 것을 확인했다.
  - 줄 세우기를 즉시 실행으로 바꾸면 "늦은 추가 응답" 테스트 실패
  - `saveNow` 가 줄을 기다리지 않으면 "업로드 중 영상 요청" 테스트 실패
  - 저장 실패 처리의 세대 검사를 빼면 "새로 불러온 뒤 늦은 409" 테스트 실패
  - 모달 초점 복귀를 빼면 모달 테스트 실패
  - 영상 만들기 버튼 비활성화를 빼면 "구조 변경 중 생성" 테스트 실패
- **동작 변화**: 이미지 업로드가 한 번에 하나씩 처리된다. 큰 이미지를 연속으로 올리면 두 번째는 첫 번째가 끝난 뒤 시작한다(응답 순서를 보장하는 대가).
- **남은 점**: 모달 뒤의 화면은 `inert` 처리하지 않았다(Tab 순환은 막지만 스크린 리더의 가상 커서는 뒤 화면에 닿을 수 있다). 좁은 화면의 편집 화면 배치도 확인하지 못했다.

## 2단계 재검수 후속 (P2 2건)

| # | 지적 | 판단 | 처리 |
|---|---|---|---|
| P2-1 | 새로 불러온 뒤 입력한 내용의 자동 저장이 멈춘다. 이전 저장이 진행 중이면 새 입력의 `flush` 가 이전 세대의 진행 중 작업(`inFlightDone`)을 기다리고, 그 응답이 세대 검사로 무시되면 새 입력을 보낼 요청이 실행되지 않아 "저장 중…"에 머문다 | 타당(이전 수정이 만든 결함) | 진행 중인 저장 작업을 **세대별**로 기록한다(`inFlight = { gen, done }`). 현재 세대가 아닌 작업은 기다리지 않고 새 작업을 따로 시작한다. 이전 작업의 `finally` 는 자기 항목만 지운다. 저장 루프도 세대가 바뀌면 멈춘다 |
| P2-2 | 이전 세대에서 줄 서 있던 이미지 요청이 새로 불러온 뒤 실행된다(응답만 무시되어, 서버 이미지는 지워졌는데 화면에는 이전 이미지가 남는다) | 타당 | 줄 서 있던 요청은 차례가 왔을 때 세대를 다시 확인하고 달라졌으면 서버로 보내지 않는다(`enqueueFor`). 이미 서버로 나간 요청은 취소할 수 없으므로 `load()` 가 줄이 빌 때까지 기다린 뒤 서버 내용을 읽어, 읽은 내용에 그 결과가 들어 있게 한다 |

- **검증**: 타입체크 통과, 단위·API·ffmpeg 137개, E2E 49개 통과(신규 1개 + 기존 1개 보강)
  - 보강: "새로 불러온 뒤 늦은 409" 테스트가 이전 저장이 진행 중인 동안 새 화면에서 입력하고, 그 입력이 저장되는지(서버 값 확인)까지 본다.
  - 신규: 업로드 요청이 서버에 닿는 데 3초 걸리는 동안 이미지 삭제를 줄 세우고 새로 불러온다 → 줄 선 삭제는 실행되지 않고(서버 이미지 유지), 화면의 두 장면 이미지가 서버와 같다.
- **변이 검사**: 진행 중 저장을 세대와 무관하게 공유하면 보강한 테스트 실패 / 줄 선 요청의 세대 검사를 빼면 신규 테스트 실패 / `load()` 가 줄을 기다리지 않으면 신규 테스트 실패(화면이 업로드 전 이미지를 보여줌). 확인 후 원복.
- **남은 점**: 이미 서버로 나간 요청의 결과를 되돌리지는 않는다(새로 불러오기가 그 결과까지 읽어 오는 방식이다). 이전 라운드의 한계는 그대로다.

- **CI 실패 기록(`291f0de`)**: 로컬은 통과했지만 CI 의 E2E 1개가 실패했다("늦게 도착한 장면 추가 응답…"). 앱 결함이 아니라 테스트의 타이밍 가정 오류였다 — 썸네일 `<img>` 요소가 생기자마자 `naturalWidth` 를 읽어서, 로드 전(0)이거나 이전 이미지(1280x720)를 읽을 수 있었다. 새 이미지(320x180)가 보일 때까지 기다린 뒤 0.8초 동안 유지되는지 확인하도록 고쳤다. 직렬화를 제거하는 변이에서는 여전히 이 테스트가 실패한다.

## 2단계 재검수 후속 2 (P2 1건)

| # | 지적 | 판단 | 처리 |
|---|---|---|---|
| P2 | 새로 불러온 뒤 입력하고 자동 저장(900ms) 전에 "← 프로젝트"로 나가면 새 입력이 저장되지 않는다. 화면을 떠날 때의 마지막 저장 조건이 `!inFlight.current` 만 보아, 이전 세대의 저장이 진행 중이면 건너뛰고 디바운스 타이머도 취소했다 | 타당(세대별 `inFlight` 로 바꿀 때 이 조건을 같이 바꾸지 않았다) | 진행 중인 저장이 **현재 세대**의 것일 때만 건너뛴다(`running.gen === loadGen.current`). 이전 세대의 저장은 응답이 무시되므로 새 입력은 언마운트 때 보낸다 |

- **검증**: 타입체크 통과, 단위·API·ffmpeg 137개, E2E 50개 통과(신규 1개). 이전 세대의 저장이 진행 중인 상태에서 새로 불러오고 → 입력 → 900ms 전에 목록으로 나가면 서버에 그 입력이 저장된다. 조건을 이전 코드로 되돌리면 이 테스트만 실패한다(확인 후 원복).
- **후속으로 남긴 것(검수 제안)**: 앱 차원의 요청 시간 제한이 없어서, 큐의 요청이 응답하지 않으면 "불러오는 중…"이 끝나지 않는다. 대기 상한과 오류·재시도 경로는 이번에 만들지 않았다. 요청 시간 제한은 큰 이미지 업로드의 정상 소요 시간과 함께 정해야 한다.
- **알려진 한계**: 화면을 떠나는 시점에 **현재 세대**의 저장이 이미 나가 있고 그 뒤에 더 입력한 변경이 있으면, 그 뒤 변경은 보내지 않는다(저장 루프가 언마운트로 멈춘다). 오래된 본문이 나중에 도착해 최신 본문을 덮는 일을 피하려는 선택이며, 이 라운드 이전부터의 동작이다.
- **테스트의 고정 대기**: 지연 라우트를 쓰는 E2E 는 고정 시간(3~5초)에 기대는 부분이 있다. 느린 CI 에서 불안정해질 수 있어, 요청 도착·응답 해제를 명시적으로 제어하는 방식으로 바꾸는 것을 후속으로 남긴다.
