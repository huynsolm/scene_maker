# 후속 기능: 장면 수 가변 — 1단계(서버)

장면을 3개 고정에서 **1~10개**로 바꾸는 작업의 서버 쪽이다. 화면(추가·삭제 버튼, 문구 정리)은 2단계에서 한다. 이 단계의 화면 변경은 기존 편집 화면이 새 API 로 계속 동작하게 하는 최소한뿐이다.

## 사용자 결정
- 장면 수 **최소 1 ~ 최대 10**, 새 프로젝트 기본 **3개**, 총 길이 상한 **300초**.
- 총 길이 300초는 장면 10개 x 30초와 같아서 별도 검사를 두지 않았다. 두 한도가 이미 보장한다(`TOTAL_MAX_SEC = SCENE_MAX * DURATION_MAX_SEC`). 한도를 바꿀 때는 이 관계를 다시 봐야 한다.
- 순서 변경은 범위 밖이다(복잡한 타임라인 제외 원칙).

## 설계
| 항목 | 내용 |
|---|---|
| 장면 식별 | 장면마다 UUID(`scenes.id`). 이미지 업로드·삭제 경로가 `/api/projects/:id/scenes/:sceneId/image` 로 바뀌었다 |
| 순서 | `position` 은 표시 순서이며 트랜잭션 안에서 0..n-1 로 유지한다. 유니크 제약은 두지 않았다(한 칸씩 당길 때 일시적으로 충돌하기 때문) |
| 추가 | `POST /api/projects/:id/scenes` → 맨 뒤에 빈 장면(길이 10초). 최대 개수에서 `SCENE_LIMIT`(422) |
| 삭제 | `DELETE /api/projects/:id/scenes/:sceneId`. 마지막 한 장면은 `SCENE_MIN`(422), 없는 장면은 404. 뒤 장면 순서를 당기고, 이미지는 장면·렌더 작업 어디에서도 쓰지 않을 때만 정리 |
| 저장 | 본문에 장면 ID 를 담으면 서버의 현재 장면 목록(순서 포함)과 같아야 한다. 다르면 `SCENES_CHANGED`(409). 추가·삭제 전에 보낸 오래된 저장이 삭제된 장면을 되살리지 못한다 |
| ID 없는 저장 | 내부 호출·하위 호환용. 현재 장면 수와 같을 때 위치 순서로 적용, 다르면 409. ID 를 일부만 보내면 400 |
| 이전(migration) | 옛 `scenes` 표(PRIMARY KEY (project_id, position), position 0..2 CHECK)를 한 트랜잭션에서 새 표로 옮긴다. 행·순서·이미지 연결을 보존하고 ID 만 새로 붙는다. 실패하면 이전 표가 그대로 남는다 |
| 렌더 | 렌더러·스냅샷·결과 화면은 이미 장면 배열 기반이라 코드 변경이 없다. 1개·5개 장면을 실제 ffmpeg 로 만들어 길이와 전환 시각을 검증한다 |

## 검증 (Node 22.23.4)
- 타입체크 통과, 단위·API·ffmpeg 133개, E2E 37개 통과
- 신규 `tests/scenes.test.ts`(10개): 기본 ID·순서, 추가·최대, 중간 삭제 시 내용·이미지 이동, 최소·404, 이미지 정리, 오래된 저장 거절(삭제·추가 양쪽), ID 일부·순서 불일치, 다른 프로젝트의 장면 ID, 장면 수가 바뀐 프로젝트의 스냅샷
- `tests/migrate.test.ts`(+1): 옛 표 이전 시 내용·순서·이미지 연결 보존, ID 고유, 임시 표 미잔존, CHECK 해제, CASCADE 유지, 재실행 시 ID 불변
- `tests/ffmpeg.test.ts`(+1): 장면 1개(4초), 5개(18초, 전환 3·7·10·15초) 실제 렌더
- 변이 검사: 장면 목록 일치 검사를 제거하면 오래된 저장 관련 3개 테스트가 실패(확인 후 원복)

## 확인하지 못한 것 / 다음 단계
- 편집 화면에는 아직 추가·삭제 UI 가 없다(2단계). 현재 화면은 서버의 장면 ID 를 저장 본문에 실어 보내고, 이미지 API 에 ID 를 쓴다.
- 자동 저장이 409 를 받았을 때 화면이 어떻게 복구할지(새로 고침 안내)는 2단계에서 정한다.
- 대용량 이미지 10장의 렌더 시간·디스크 사용량은 측정하지 않았다.
