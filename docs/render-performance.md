# 영상 생성 성능 측정 (장면 최대 10개)

> 이 문서는 측정에서 발견한 문제(큰 사진이면 제한 시간 초과)와 그 수정(이미지 사전 줄이기)을 함께 기록한다.

`npm run measure:render` (`scripts/measure-render.ts`)로 쟀다. 실제 앱의 렌더 경로(작업 큐 → ffmpeg)로 케이스마다 영상을 한 번 만들고, 걸린 시간·ffmpeg 최대 메모리·임시 폴더 최대 크기·완성 파일 크기를 잰다. `--only A,B`로 케이스를 고를 수 있다.

**환경**: 4 코어(Intel Xeon @ 2.10GHz), 메모리 16GB, ffmpeg 6.1.1, 클라우드 샌드박스. 숫자는 이 환경의 것이고 사용자의 컴퓨터에서는 달라진다(보통 더 빠르지만 알 수 없다). 영상 내용은 합성 이미지라 완성 파일 크기는 실제 사진 영상보다 작게 나올 수 있다.

## 결과 (이미지 사전 줄이기 전 → 후)

같은 환경·같은 케이스를 사전 줄이기 적용 전과 후에 각각 쟀다.

| 케이스 | 영상 길이 | 걸린 시간 (전 → 후) | 실시간 대비 (후) | ffmpeg 최대 메모리 (전 → 후) | 임시 폴더 최대 (전 → 후) | 완성 파일 | 결과 (전 → 후) |
|---|---|---|---|---|---|---|---|
| A. 3장면 x 10초, 1280x720 PNG | 30초 | 11.4초 (변경 없음, 후 미측정) | 0.38배 | 367MB | 0.0MB | 0.2MB | 성공 |
| B. 10장면 x 3초, 1280x720 PNG | 30초 | 13.7초 (변경 없음, 후 미측정) | 0.46배 | 744MB | 0.3MB | 0.2MB | 성공 |
| C. 10장면 x 30초(최대 길이), 1280x720 PNG | 300초 | 100.6초 → 94.7초 | 0.32배 | 768MB → 685MB | 1.8MB → 2.9MB | 2.0MB | 성공 → 성공 |
| **D. 10장면 x 30초 + 4096x4096 JPEG(약 8.6MB)** | 300초 | **603.3초(제한 초과) → 143.4초** | 0.48배 | 2351MB → 1023MB | 1.8MB → 30MB | 8.0MB | **실패 → 성공** |
| **E. 3장면 x 10초 + 휴대폰 사진 4032x3024 JPEG** | 30초 | **162.2초 → 16.3초** (10배) | 0.54배 | 681MB → 449MB | 0.8MB → 7.4MB | 0.9MB | 성공 → 성공 |
| **F. 10장면 x 10초 + 휴대폰 사진** | 100초 | **558.7초 → 53.0초** (10.5배) | 0.53배 | 1830MB → 1039MB | 2.7MB → 24MB | 2.7MB | 성공(제한 600초에 7% 차이) → 성공 |

- 큰 사진 케이스는 이제 영상 길이의 약 절반 시간에 끝난다(0.48~0.54배). 작은 PNG(C)와 같은 수준이다.
- ffmpeg 최대 메모리가 줄었다(D 2.3GB → 1.0GB). 서버 프로세스 메모리는 약 200~250MB로 변함없다.
- **대가**: 임시 작업 폴더가 커진다. 장면마다 프레임 크기의 무손실 PNG를 두기 때문이며, 사진은 장면당 약 2~3MB(D에서 최대 30MB)다. 작업이 끝나면 임시 폴더는 지워진다. 장면 10개 x 사진이면 수십 MB로 디스크 부담은 여전히 작다.
- 장면 화면과 MP4 저장은 ffmpeg 한 번의 호출이라 단계별 시간은 의미가 없다.

## 발견했던 문제와 원인 (적용 전)

렌더러는 장면 이미지를 `-loop 1 -i <이미지>`로 읽는다. 이 방식은 **프레임마다 이미지 파일을 다시 디코딩**하고 그 뒤 `scale`이 1280x720으로 줄인다. 720p PNG는 디코딩이 싸지만 약 1,670만 픽셀 JPEG는 프레임마다 약 0.23초가 든다(300프레임 장면 하나가 70초). 디코딩 결과는 모든 프레임에서 같으므로 낭비였다. 휴대폰 사진 10장짜리 영상(F)이 559초로 제한 시간 600초에 닿을 만큼 느렸고, 앱이 허용하는 최대 조건(D)은 제한 시간 안에 끝나지 않았다.

장면 하나(10초, 300프레임)를 직접 잰 결과:

| 입력 | 걸린 시간 |
|---|---|
| 큰 사진(4096x4096 JPEG 6.6MB)을 그대로 `-loop 1` | 70.2초 |
| 1280x720 PNG를 `-loop 1` | 2.4초 |
| 큰 사진을 한 번만 1280x720으로 줄인 PNG로 바꾼 뒤(줄이는 데 0.6초) | 4.9초 |

## 적용한 변경

`server/render/renderer.ts`: 렌더 첫 단계(이미지가 읽히는지 확인하던 단계)가 이제 장면 이미지를 **한 번만** 디코딩해 프레임 크기(가로세로를 채우도록 확대한 뒤 가운데 자르기, RGBA, 무손실 PNG)로 줄여 작업 폴더에 `frame<i>.png`로 둔다. 본 렌더는 원본 대신 이 파일을 `-loop 1`로 읽는다. 읽을 수 없는 이미지는 예전처럼 몇 번째 장면인지 알려 주며 실패한다. 줄이는 필터는 예전에 본 렌더의 필터 그래프에서 하던 것과 같고 필터 그래프는 그대로 두었다(입력이 이미 프레임 크기라 `scale/crop`은 사실상 통과).

### 결과가 같음을 확인한 방법
- **바이트 비교**: EXIF 회전 JPEG, 반투명 PNG, 세로 WebP, 가로 JPEG, 작은 PNG, 큰 사진(3000x2000)이 섞인 6장면 영상을 변경 전 코드와 변경 후 코드로 각각 만들어 `cmp`로 비교했다. **337,592바이트, 완전히 동일**했다.
- **기존 렌더 테스트 전체 통과**: 자막 위치, 실제 JPEG·WebP·PNG, EXIF 회전·투명 PNG 합성, 장면 1개·5개의 전환 시각, 깨진 이미지의 장면 번호 안내, 제한 시간 정리 등(`tests/ffmpeg.test.ts`), 브라우저 E2E 59개(미리보기↔영상 자막 일치 포함).
- **신규 속도 회귀 테스트**(`tests/ffmpeg.test.ts`): 4096x4096 사진 장면이 작은 이미지 장면의 10배 안에 끝나야 한다(변경 후 약 2~4배). 원본을 그대로 `-loop 1`로 읽도록 되돌리면 20.8배(작은 이미지 1.7초, 큰 사진 36.5초)로 실패하는 것을 확인했다. 절대 시간이 아닌 비율이라 느린 환경에서도 흔들리지 않는다.

## 한계

- 한 대의 4코어 환경에서 케이스당 한 번 쟀다(반복 평균 아님). 같은 케이스의 편차는 확인하지 않았다.
- 합성 이미지(testsrc2 + 잡음)를 썼다. 실제 사진은 JPEG 압축률과 디코딩 비용이 다를 수 있다. 바이트 동일 비교도 이 합성 6장면 한 세트 기준이다.
- 변경 전(A, B)과 변경 후(C~F)의 측정 시점이 달라 사이에 환경 편차가 있을 수 있다. C는 변경과 무관하게 비슷한 시간(100.6초 → 94.7초)이라 편차 수준을 보여 준다.
- 동시에 여러 영상을 만드는 경우는 재지 않았다(작업 큐가 한 번에 하나만 처리한다).
- 디스크는 임시 폴더와 완성 파일만 쟀다. 업로드한 원본 이미지의 누적(프로젝트당 최대 10장 x 10MB)은 따로 보지 않았다.
