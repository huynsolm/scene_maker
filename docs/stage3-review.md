## 2. 구현 내용

### 결과 화면 (`web/screens/ResultScreen.tsx`, 디자인 README 3절)
- 상단바: ← 프로젝트 / 제목 / 상태 배지 / [편집 화면으로 돌아가기]. 본문 `max-width 1240`, 왼쪽 미디어 카드 + 오른쪽 상태 패널(좁으면 줄바꿈).
- **완료**: 실제 영상 플레이어(16:9), 재생/일시정지, **장면 길이 비율로 나뉜 진행 막대**(누르면 그 장면의 처음으로 이동), `0:12 / 0:30`, 영상을 눌러도 재생/정지. 정보 목록(MP4 / 1280 × 720 / 길이 / 소리 없음 / 완성 시각), 48px "MP4 다운로드"(파일명 = 제목.mp4, 토스트), [수정하러 편집 화면으로].
- **편집용 안내선(자막 안전 영역)은 결과 플레이어에 그리지 않는다** — E2E 가 `.guide-box`·`.subtitle-hint` 가 0개임을 확인.
- **대기·생성 중**: 움직이는 막대(진행률을 알 수 없으므로 퍼센트·남은 시간 없음 — E2E 가 `%` 가 없는지 확인), 4단계 목록(✓ 완료 / 회전 스피너 / 대기 원), 비활성 "영상 만들기 요청됨". 1.5초 폴링.
- **실패**: 오류 박스(원인 제목, 해결 방법, 오류 코드·시각), "다시 시도", "편집 화면에서 확인하기" 힌트. 문제 장면이 있으면 **"장면 N 편집에서 확인하기"** 가 `?scene=N` 으로 편집 화면을 열어 해당 장면을 미리 선택한다(서버가 오류에 `scene` 을 구조화해 저장: `render_jobs.error_scene`).
- 접근성: 상태 패널 `aria-live="polite"`, 오류 `role="alert"`, 진행 막대 버튼에 `aria-label`, `prefers-reduced-motion` 에서는 회전·이동 애니메이션을 멈추고 상태를 글자로 구분.
- 라우트: `/projects/:id/result`(가장 최근 작업) · `/projects/:id/result/:jobId`(특정 작업, "마지막 생성 영상 보기").

### 서버 변경
- `GET /api/projects/:id/renders/:jobId`(프로젝트 소속 검증, 9절). `Project.lastVideo`(가장 최근 완성 작업), `RenderJobView.outdated`(요청 뒤에 프로젝트 내용이 고쳐졌으면 true), `error.scene`. `render_jobs` 에 `error_scene` 컬럼(자동 마이그레이션).
- 새 영상이 실패해도 `lastVideo` 는 직전 완성 영상을 가리킨다. 새 영상이 완성되면 그쪽으로 바뀐다(테스트).

### 자막 글꼴
- 영상에 쓰는 `fonts/NotoSansKR-SemiBold.ttf` 에서 한글 완성형 전체 등 화면에 필요한 글자만 남긴 `web/public/fonts/NotoSansKR-SemiBold.subset.woff2`(563KB, OFL 사본 포함). 만드는 법: `scripts/make-web-font.py`.
- 편집 화면에 들어올 때 글꼴을 미리 받는다(자막이 처음 그려질 때의 깜빡임을 줄임).

### 이미지 처리 보강(렌더러)
- **투명 PNG**: 프레임 배경색(`#1B1C20`, 미리보기와 같은 색) 위에 합성한다. 이전에는 알파를 무시해 반투명 흰색이 순백으로, 투명 영역은 그 아래 숨은 색(예: 빨강)이 그대로 보였다.
- **EXIF 회전 JPEG**: 확인 결과 ffmpeg 가 이미 자동 적용해 브라우저 미리보기와 같은 방향이다(코드 변경 없음, 회귀 테스트만 추가).

## 3. 이번 단계에서 테스트·측정이 잡은 결함

| 결함 | 발견 경로 | 처리 |
|---|---|---|
| 웹 글꼴 부분집합이 `kern` 외 레이아웃 기능(`locl` 등)을 지워 글자 폭이 9~13px 좁아짐 | 미리보기↔영상 측정에서 전체 글꼴 대비 차이 | 전체 기능 유지로 재생성 → 차이 3px 이하. 이전 방식으로 되돌리면 E2E 가 실패하는 것도 확인 |
| 투명 PNG 의 알파 무시(순백/숨은 색 노출) → 미리보기와 영상이 다름 | 이미지 종류 확인 | 프레임 배경 위 합성 |
| 합성 도입 직후 영상이 장면마다 한 프레임씩 짧아짐(30.0 → 29.9초) | 기존 길이 검사가 실패 | `tpad`로 복제 후 `trim`으로 정확한 프레임 수(길이×fps)에 맞춤. 3·10·30초 모두 정확 |
| 링크 모양 버튼(`← 프로젝트` 등)에 밑줄 | 화면 캡처 확인 | `a.btn { text-decoration: none }` |
| CI 에서만 `frame-match` 가 실패(상자 폭 6px > 허용 5px) | 첫 CI 실행(GitHub Actions) | **앱 결함 아님**. 브라우저 글자 힌팅 차이(`--font-render-hinting=full` 로 로컬에서 같은 6px 재현). 검사 브라우저의 힌팅을 `none` 으로 고정하고 힌팅별 차이(최대 약 7px)를 frame-comparison.md 에 기록 |
| 다운로드 파일명이 `download` 로 저장됨 | 결과 화면 E2E | **앱 결함 아님**: 서버 헤더(`filename*=UTF-8''…`)는 올바르다. `LANG` 이 비어 있는 Linux(POSIX 로케일)에서는 Chromium 이 한글 파일명을 만들지 못한다(`LANG=C.UTF-8` 이면 정상). 테스트 브라우저를 UTF-8 로케일로 띄움(`e2e/harness.ts`). 일반 사용자 OS 는 UTF-8 이라 영향 없음 |

(2단계의 같은 틱 더블클릭 중복 요청 수정은 stage2-review 참고.)

## 4. 전체 흐름 점검 (`e2e/flow.e2e.ts`, UI 만으로)
빈 목록 → 첫 영상 만들기 → 제목 입력, 장면 3개의 문구·이미지 업로드·길이 입력(다음 장면 버튼 사용) → 미리보기 재생(진행 시간 증가)·안내선 켜기/끄기 → 저장됨 → **새로고침 후 유지** → 확인 모달(준비됨 3개) → 시작 → **목록으로 나가도 생성 계속, 목록에서 상태 확인(생성 완료까지)** → 행 클릭으로 결과 화면 → 재생 → 다운로드(제목.mp4) → 편집으로 돌아가 문구 수정 → 마지막 생성 영상 보기(이전 버전 안내) → 다시 만들기(새 영상, 안내 사라짐, 작업 2개) → 삭제(안내 문구 → 이미지·영상 파일까지 삭제).
실패 동선은 `e2e/result.e2e.ts`: 깨진 이미지 → 실패 이유 → 직전 영상 링크 → 문제 장면으로 이동 → 이미지 교체 → 재시도 성공.

## 8. 확인하지 못한 것 / 한계
- **일반 UI 글꼴 Pretendard**: CDN 이 이 환경에서 열리지 않아 실제 CDN 렌더링은 확인하지 못했다(대체 글꼴로 테스트). 자막은 자체 호스팅이라 영향 없음.
- **웹 자막 글꼴 범위**: 한자·이모지는 부분집합에서 제외했다. 미리보기에서는 시스템 글꼴로 대체되어 영상(전체 Noto Sans KR)과 글자 모양·폭이 다를 수 있다. 이모지는 Noto Sans KR 자체에 없어 영상에서도 대체 글꼴 처리이며 미테스트.
- **이미지**: EXIF 회전은 orientation 6 한 가지만, 투명도는 PNG 만 확인했다(WebP 알파, 16비트·CMYK JPEG, 애니메이션 WebP 미확인).
- **접근성**: aria 속성과 `prefers-reduced-motion` CSS 는 넣었지만 키보드 조작·스크린리더는 직접 확인하지 않았다.
- **글자 힌팅**: 사용자 브라우저의 힌팅 설정에 따라 미리보기와 영상의 상자 폭이 최대 약 7px(0.5%) 달라질 수 있다(영상은 영향 없음). 자세한 수치는 frame-comparison.md.
- **환경**: Windows, Chromium 외 브라우저(Safari 의 H.264 재생 등), 실제 모바일 기기는 미확인. 비 UTF-8 로케일의 Linux 브라우저는 한글 다운로드 파일명이 `download` 로 저장된다(브라우저 한계).
- **부하**: 큰 이미지(4096×4096) 인코딩 시간·메모리, 디스크 부족, 동시 요청 부하 미확인. 큐는 한 번에 1개만 처리한다.
- 편집 화면의 "마지막 생성 영상 보기"는 화면을 연 시점의 정보라, 열어 둔 채로 다른 탭에서 영상이 새로 완성되면 새로고침해야 바뀐다.
- 영상·이미지 자동 정리 정책은 첫 버전 결정대로 두지 않았다(프로젝트 삭제 때만 지움). 이미지를 자주 교체하거나 재생성을 많이 하면 디스크가 늘어난다.

## 9. 검수 후속 수정

### P1 — 결과 주소가 작업 ID 의 프로젝트 소속을 검증하지 않음
- **문제**: `/projects/A/result/<B 의 작업 ID>` 를 열면 화면이 작업 ID 만으로 조회해(`GET /api/renders/:id`), A 프로젝트 화면에 **B 프로젝트의 제목·구성 장면·영상**이 그대로 표시됐다.
- **수정**
  - 서버: `GET /api/projects/:id/renders/:jobId` 를 추가. 작업이 그 프로젝트의 것이 아니면 404(내용을 돌려주지 않음). 결과 화면은 이제 이 경로만 쓴다. (`latest` 는 작업 ID 로 해석되지 않고 기존 동작 유지.)
  - 화면: 응답의 `projectId` 가 주소의 프로젝트와 다르면 그리지 않는 이중 방어, 404 면 "영상을 찾을 수 없어요"(편집 화면·목록 링크) 안내.
- **검증**: API 테스트(같은 프로젝트 200 / 다른 프로젝트 404, 응답에 작업 ID·영상 주소 미포함 / 없는 작업·프로젝트 404 / `latest` 유지)와 E2E(A 경로 + B 작업 ID → B 의 제목·문구·플레이어 없음).
  변이 검사: 서버 검사만 제거 → API 테스트 실패 / 서버·화면 방어를 모두 제거(원래 취약점) → E2E 실패 / 서버 검사만 제거(화면 방어 유지) → E2E 통과(이중 방어 확인). 확인 후 원복.
- **남은 범위**: `GET /api/renders/:id` 와 영상 파일 경로 `/api/renders/:id/video` 는 작업 ID 만으로 접근한다. ID 는 서버가 만든 UUID 이고 로그인 없는 단일 사용자 앱이라 그대로 두었다(다중 사용자로 확장할 때는 이 경로들도 소유자 검증이 필요하다).

### 성능 — 자막 레이아웃이 최악의 입력에서 서버를 수 초~수십 초 멈춤
- **발견**: 위 수정 뒤 전체 테스트에서 `layout` 단위 테스트 1개가 5092ms 로 vitest 기본 제한(5초)에 걸려 실패했다. 이전에는 통과해서 간헐 실패로 보였지만, 실제 원인은 성능이었다.
- **원인**: `opentype.js` 의 `getAdvanceWidth` 한 번이 약 2.4ms. 호출마다 대형 CJK 글꼴(글리프 약 2만 5천 개)의 치환 규칙을 처음부터 다시 적용한다. 레이아웃(줄바꿈 균형 탐색)은 호출을 수천 번 하므로 **200자 일반 문장 3.0초, 붙여쓰기 80자 5.1초, 200자 붙여쓰기 11.7초** — 렌더 준비가 동기 계산이라 그동안 서버 전체가 멈췄다.
- **수정**: 글자별 advance 와 글자쌍 조정값을 직접 합산(쌍 단위 캐시). 같은 입력이 12ms / 14ms / 9ms 로 줄었다. 폭은 **당시 사용하던 `opentype.js` 측정과 같았지만**(샘플·영문 혼합·`AV To Yo`·`fi ffi` 문구에서 0.00px), 이것이 렌더 엔진(HarfBuzz)과 같다는 뜻은 아니었다 — 아래 P2 참고.
- **검증**: 성능 회귀 테스트(최악 입력 3종이 각 0.5초 안), 기준값 고정 테스트(기존 방식으로 구한 폭), 그리고 폭 측정이 바뀐 뒤에도 영상 상자 ±4px 검사·미리보기↔영상 일치 E2E 가 그대로 통과.

### P2 — 글자별 합산이 GSUB 치환을 무시해 일부 입력에서 폭이 렌더와 달라짐 (검수 지적, 타당)
- **정정**: 위 성능 수정에서 "기존 방식과 폭이 같다"는 `opentype.js` 의 측정과 같다는 뜻이었다. `opentype.js` 도 HarfBuzz 가 아니므로, 직접 합산이 "모든 입력에서 렌더(libass/HarfBuzz)와 동일"하다고 말할 수 없었다.
- **확인 방법**: 추측하지 않고, 서버 측정값을 브라우저(Chromium 의 HarfBuzz — libass 와 같은 shaping 엔진)의 폭과 입력 종류별로 직접 대조했다(`e2e/measure-parity.e2e.ts`, 40.96px 기준, 힌팅 고정).

| 입력 종류 | 서버 − 브라우저 | 처리 |
|---|---:|---|
| 한글 NFC 문장 · 라틴 문장 · 글자쌍 조정 · 숫자·문장부호 · NBSP · NFC 결합 문자 | 0.0 ~ 0.2px | **보장 범위** |
| **분해된 한글 자모(NFD)** | **+980 ~ +1206px** | **수정**: NFC 로 합침 → 0.14px |
| 제로폭 공백·접합자·변이 선택자 | 문자당 +41px(`.notdef` 폭을 셈) | **수정**: 보이지 않는 문자 제거 → 0.02px |
| 라틴 합자 후보(`fi fl ffi ffl`) | +3.1px(0.4%) | **한계로 문서화**, 상한 5px 로 감시 |
| 전각 문자 | +20.6px(5%) | **한계로 문서화**, 상한 25px 로 감시 |
| 옛한글 자모 조합 | +188px | **미보장**(글꼴 GSUB 필요) |
| 이모지 | −10px | **미보장**(글꼴에 없음, 대체 글꼴 폭을 알 수 없음) |

- **가장 심각했던 것은 NFD**: macOS 등에서 복사·붙여 넣은 한글이 분해된 자모일 수 있고, 이때 서버가 폭을 2배 이상으로 계산해 줄바꿈과 상자 폭이 크게 틀어졌다(`+980px`). 사용자가 실제로 만날 수 있는 입력이다.
- **수정**
  - `server/render/layout.ts` `normalizeSubtitleText`: NFC + 보이지 않는 문자·제어 문자 제거(줄바꿈·일반 공백·NBSP 는 유지). 레이아웃과 ASS 로 나가는 줄이 모두 이 정리를 거친다.
  - `shared/schemas.ts`: 제목·문구를 저장할 때 NFC 로 합친 뒤 글자 수 한도를 센다(분해된 자모는 글자당 2~3 칸이라 한도를 일찍 넘긴다). **→ 이 단계에서는 NFC 만 적용했고 보이지 않는 문자는 저장 경계에 적용하지 않았다. 아래 "P2 후속"에서 바로잡았다.**
  - `web/screens/Editor.tsx`: 붙여 넣는 순간 NFC 로 합친다. 기존에는 NFD 150자를 붙이면 450 칸이라 `maxLength=200` 에서 **뒤가 말없이 잘렸다**(같은 원인의 입력 결함). IME 조합 중에는 건드리지 않는다.
- **shaping 엔진(HarfBuzz) 도입은 하지 않았다**: 대조 결과 보장 범위 밖의 입력만 어긋나므로, 정규화와 명시적 한계가 비용 대비 적절하다고 판단했다. 옛한글·이모지·전각·합자가 중요한 요구가 되면 `harfbuzzjs`(WASM)로의 전환이 다음 선택지다.
- **검증**
  - 단위: NFD/NFC 레이아웃 동일, 제로폭·제어 문자 무시, 정규화 함수, 저장 API 의 NFC·한도(`tests/layout.test.ts`, `tests/projects.test.ts`)
  - 실제 렌더: NFD 문구를 렌더해도 영상의 상자 크기가 NFC 설계값과 ±4px(`tests/ffmpeg.test.ts`)
  - 브라우저 대조: 보장 범위 12종이 1px 안, 알려진 한계가 상한 안, 미보장 항목은 값만 출력(`e2e/measure-parity.e2e.ts`)
  - 붙여넣기: NFD 150자를 붙여 넣어 150자가 모두 남고 새로고침 후에도 유지(`e2e/editor.e2e.ts`)
  - 변이 검사: 정규화를 제거하면 단위 테스트 3개가 실패하고 대조 테스트가 `+979.9px` 를 드러냄. 확인 후 원복.
- **측정 보장 범위(명시)**: 서버 폭 측정이 렌더와 맞는 것은 **NFC 한글, 라틴, 숫자, 일반 문장부호**다. 그 밖(옛한글·이모지·전각·합자·글꼴에 없는 문자)은 줄바꿈과 상자 폭이 달라질 수 있다.

### P2 후속 — 보이지 않는 문자 제거를 저장 경계에도 적용 (검수 지적, 타당)
- **문제**: 위 정리를 영상 파이프라인(`layoutSubtitle`)에서만 하고 저장 경계에는 NFC 만 적용했다. 그래서
  1. 문구에 `가\u200B나다` 를 저장하면 **DB 에는 제로폭 문자가 남고** 렌더는 이를 제거 → 저장값·미리보기·영상이 서로 다른 문자열을 본다.
  2. 보이는 글자 200개 + 제로폭 문자 1개는 **영상에서 제거될 문자 때문에 API 200자 한도에 걸려 400** 이었다.
  (둘 다 수정 전에 그대로 재현: 저장값에 `200b` 가 남음 / 400)
- **수정**: 정리 규칙을 `shared/text.ts`(`cleanText`, `cleanTitle`)로 옮겨 **한 곳에서** 정의하고 모두 같은 함수를 쓴다.
  - 저장 스키마(`shared/schemas.ts`): 정리한 뒤 글자 수를 센다. 제목은 `cleanTitle`(줄바꿈·탭은 공백).
  - 붙여넣기(`web/screens/Editor.tsx`): 저장 때와 같은 규칙으로 정리 → 글자 수 표시와 `maxLength` 에 제로폭 문자가 들어가지 않는다.
  - 영상 파이프라인(`server/render/layout.ts`): 같은 `cleanText` 를 한 번 더 적용(이전에 저장된 값이나 저장을 거치지 않는 경로 방어).
  - 부수 정리: CRLF·단독 CR 은 `\n` 으로 통일(이전에는 영상 쪽에서 단독 CR 이 삭제됐다).
- **검증**: 단위(`tests/text.test.ts`: NFC, 보이지 않는 문자 11종, 제어 문자·줄바꿈·탭, 보이는 문자 유지, 멱등), 저장 API(제로폭 저장 안 됨 / 보이는 200자 + 제로폭은 저장 / 보이는 201자는 400 / CRLF 통일·제목 한 줄), 붙여넣기 E2E(제로폭이 섞인 글이 글자 수·저장값에 남지 않음). 변이 검사: 저장 경계를 NFC 만으로 되돌리면 API 테스트 3개가 실패. 확인 후 원복.
- **남은 점**: 이미 저장된(수정 전) 문구에 제로폭 문자가 있으면 DB 에는 남아 있고 영상 파이프라인이 제거한다. 일괄 정리(마이그레이션)는 하지 않았다 — 사용자 데이터를 바꾸는 작업이고 화면·영상 결과는 이미 같기 때문. 필요하면 별도로 요청해 주세요.

## 10. Node 최소 버전 상향 (보안)
- 요구: Node 보안 이슈로 **22.23.4 이상**을 써야 한다. 공식 배포 목록(nodejs.org/dist/index.json)에서 `v22.23.4`(2026-10-20, 22.x LTS)가 존재함을 확인했다.
- 변경: `package.json` `engines` 를 `>=22.23.4 <23` 으로, `.nvmrc` 를 `22.23.4` 로, CI 도 `.nvmrc` 를 읽어 **최소 버전**으로 실행한다(최소 버전에서 계속 통과하는지 확인). 22.23.4 보다 낮은 Node(예: 22.22.0)와 23 이상은 `npm ci` 가 `EBADENGINE` 으로 설치 초기에 중단한다(`.npmrc` 의 `engine-strict=true`).
- 이후 22.x 패치 버전은 그대로 허용된다. 최소 버전을 더 올려야 하면 `package.json`·`.nvmrc` 두 곳만 고친다.

  - 붙여넣기가 개입한 경우에만 브라우저 기본 되돌리기(Ctrl+Z) 기록이 끊긴다(검수에서도 수용 가능한 절충으로 평가).
  - 드래그 앤 드롭·자동 완성 같은 비-`paste` 입력은 정리된 값이 저장 뒤에 반영된다(그 전까지는 화면에 원문이 보임). 입력 중 값을 바꾸면 IME 가 깨지므로 즉시 반영은 하지 않았다.
  - 검수 환경의 `npm ci` 실패(Windows 에서 `better-sqlite3` 의 암묵적 `node-gyp rebuild`)는 재현하지 못했다. 락파일에 `better-sqlite3` 의 설치 스크립트 표시(`hasInstallScript`)가 없고 레지스트리 메타데이터도 `gypfile=false`·설치 스크립트 없음이라, 저장소 설정이 `node-gyp` 를 유발하지 않는다. 검수자가 쓴 `npm ci --ignore-scripts` 는 번들된 `prebuilds/` 를 쓰므로 유효한 우회로로 보이며, Linux/Node 22.23.4 의 깨끗한 복제본에서 같은 방식으로 설치해 typecheck·build·단위 테스트가 통과하는 것을 확인했다.

## 12. 재검수 후속 2 (P2 3건, P3 1건) — 모두 반례를 재현하거나 같은 입력으로 확인

| # | 지적 | 판단 | 처리 |
|---|---|---|---|
| P2-1 | 정리 함수가 멱등이 아님: `\u1100\u200B\u1161` 은 첫 호출에서 `1100 1161`(2칸), 두 번째에서 `가`(1칸). 구 데이터는 스냅샷과 영상 문자열이 달라지고, 이런 입력 200회는 정리 후 200자인데 스키마가 거절 | 타당(재현: 첫 호출 `1100 1161` / 두 번째 `ac00`, 스키마 거절) | `cleanText` 를 **제거한 뒤 마지막에 NFC** 로 바꿨다. NFC 를 먼저 하면 제거 문자로 떨어져 있던 자모가 합쳐지지 않은 채 남았다. 이제 반환값이 항상 NFC 이므로 멱등이다 |
| P2-2 | IME 조합 중 도착한 저장 응답은 조합이 끝나도 반영되지 않음(화면 `매\u200B장`, 서버 `매장`, 상태는 "저장됨", `saveNow()` 도 재전송 안 함) | 타당 | 조합 중 응답과 그 응답의 편집 버전을 보관(`pendingSync`)하고, 조합이 끝난 **한 틱 뒤** 아직 최신 버전이면 반영한다. 그 사이 더 입력했으면(버전이 달라졌으면) 오래된 응답으로 덮어쓰지 않고 버린다 — 이어지는 저장이 최신 내용을 다시 보내 수렴한다 |
| P2-3 | 한도에 찬 제목 앞에 붙여 넣으면 기존 뒷글자가 삭제됨(선택 영역 밖의 기존 문자열까지 합쳐 전체를 절단) | 타당 | `pasteInto`(`web/paste.ts`)가 한도를 **삽입하는 글에만** 적용한다. 선택 영역 밖의 앞·뒤 글은 지우지 않고, 남은 자리만큼만 넣으며(서로게이트 쌍은 쪼개지 않음) 자리가 없으면 아무것도 넣지 않는다(브라우저 `maxLength` 기본 동작과 같다). 제목·문구 공통 |
| P3 | 기존 앞부분이 정리되면 커서 위치가 틀림(`\u200BABC` 에서 A 뒤에 `\u200BX` → 커서가 B 뒤) | 타당 | 커서를 정리·합쳐진 값 기준의 삽입 끝(`clean(앞부분 + 삽입분).length`)으로 계산한다 |

- **검증**
  - 단위 `tests/text.test.ts`: 검수 반례, 200회 입력, 무작위 조합 3만 개(고정 시드)에서 `cleanText`·`cleanTitle` 의 멱등·항상 NFC·제거 대상 미잔존. (경험적 검사이며 증명은 아니다.)
  - 단위 `tests/paste.test.ts`(8개): 개입하지 않는 경우, 꽉 찬 제목 앞 붙여넣기에서 뒷글자 보존, 남은 자리만, 선택 영역 치환, 커서, 이모지 경계, 경계에서 자모 합쳐짐, NFD 붙여넣기
  - E2E `e2e/editor.e2e.ts`: 실제 입력칸에서 붙여넣기 3경우(제목 보존·부분 삽입·커서 2), IME 조합(합성 `compositionstart/end` 이벤트): ① 조합 중에는 값이 그대로 ② 조합이 끝나면 정리된 값으로 맞춰짐 ③ 조합 종료와 마지막 입력이 **같은 틱**에 오면 최신 입력을 지우지 않고 수렴
  - 변이 검사(각각 되돌리면 실패, 확인 후 원복): NFC 먼저 → 단위 3개 실패 / 이전 붙여넣기 알고리즘 → 단위 4개 실패 / 조합 종료 시 미반영 → E2E 실패 / 버전 확인 없이 반영 → E2E 실패
- **테스트가 먼저 놓친 것(기록)**: 조합 종료와 마지막 입력을 별도 `evaluate` 로 보내서 그 사이에 타이머가 먼저 돌았고, "버전 확인 없이 반영"하는 변이가 **통과**했다. 같은 틱에 보내도록 고친 뒤 그 변이가 실패하는 것을 확인했다. 변이 검사가 테스트의 빈틈을 드러낸 사례다.
- **남은 점**
  - 실제 OS IME(한글 조합)는 직접 조작하지 않았다. 조합 상태와 응답 순서는 합성 이벤트로 제어해 검증했다.
  - `Store` 직접 호출에는 글자 수 제한이 없다(스키마가 정리 후 길이를 검사). 정리가 멱등·NFC 가 되면서 정리 후 길이가 줄기만 하므로 스키마 검사를 우회해 한도를 넘기는 경로는 확인하지 못했다.
  - 검수 환경에는 ffmpeg 가 없어 ffmpeg 테스트 9개와 E2E 는 CI 기록으로 확인한다.

## 13. 재검수 후속 3 (P2 1건)
